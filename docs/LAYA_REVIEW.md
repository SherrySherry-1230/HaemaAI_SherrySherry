# Laya 검토와 쩜 업데이트

기획팀이 합의한 흐름에 따라 쩜의 최초 생성과 새 대화에 따른 내용 수정을 Laya가 검토한다. 해마.ai는 다음 대화에서 기존 태그와 이유를 먼저 참고하고, 새 근거를 반영한 뒤 다시 검토를 받는다. 검토용 영구 버전 번호는 추가하지 않으며 사람이 읽을 수 있는 날짜·시각·시간대 하나를 기록한다.

## 판정과 처리 상태

| 항목 | 의미 |
| --- | --- |
| `정상` | 제공된 근거로 내용을 확인할 수 있고 오류·충돌 의심이 없다. 검토 당시 입력에 대한 판단이다. |
| `이상함` | 같은 대상·시점의 오류나 충돌, 잘못 연결한 발화 근거가 의심된다. |
| `정보 부족` | 대상·시점·직접 근거가 부족해 정상 여부를 판단할 수 없다. |
| `pending` | 검토를 기다리는 처리 상태다. 판정은 없다. |
| `failed` | 엔진 실행 또는 결과 확인에 실패한 처리 상태다. 판정은 없다. |
| 필드 없음 | 이전 파일의 미검토 상태다. 읽기만으로 정상이나 대기 기록을 만들어 넣지 않는다. |

`JJum.layaTag`는 `state`, `reason`, `timestamp`와 완료 상태의 `verdict`를 갖는다. `state:'reviewed'`에서만 세 판정 중 하나가 필요하다. `pending/failed`에는 `verdict` 자체가 없어야 한다. 이유는 공백뿐인 문자열을 허용하지 않으며 문자열 길이 기준 최대 500이다. 일반 분류인 `jjtags`와 검토 정보는 분리한다.

코어가 기록하는 시각은 `2026-10-10T09:30:00.000+09:00`과 같은 한국 시간 ISO 문자열이다. 이 **하나의 `timestamp`**가 대기 전환 또는 검토 완료·실패 시각을 나타낸다. 완료 시각은 모델 응답을 받은 뒤 실제 시계로 작성한다. 기존 사실·사건·편집 이력 시각과 발화의 `occurredAt/receivedAt/recordedAt`은 그대로 유지한다. 스키마의 기존 `schemaVersion=4`도 검토 버전으로 사용하지 않는다.

## 생성과 이후 대화

1. `createJJum()`은 판정 없이 `pending`을 만든다. `processConversationToStorage()`는 쩜의 내용·언급 기록·관계를 저장한 뒤 선택적으로 주입된 `reviewEngine`을 호출한다.
2. 이후 대화에서는 기존 회상 규칙으로 같은 사용자의 쩜을 찾는다. 추출 준비 조회에 `touch:false`를 적용하여 이 조회 자체로 회상 횟수를 늘리지 않는다.
3. 표준 AI 어댑터는 기존 `layaTag`와 이유를 기억 내용 및 새 대화보다 먼저 제시한다. 태그는 보조 판단 자료이며 지시문이나 확정 사실로 취급하지 않도록 요청한다. 미검토·대기·실패를 최신 정상으로 해석하지 않는다.
4. 새 확정 발화의 `mentions`가 있는 초안으로 기존 쩜을 갱신한다. 기존 사실의 텍스트·시각·출처를 남기고 새 사실을 추가하며, 실제 내용이 바뀌면 요약을 갱신한다. 시간에 따른 실제 변화나 명시적 정정을 오류와 구별하도록 요청한다.
5. `editHistory`에 `memo`, `evidence:{conversationId,utteranceIds}`, `reviewRequested:true`를 남기고 이전 판정을 `pending`으로 바꾼다. 추출 AI의 `updateMemo`가 없으면 코어가 해당 작업의 기본 메모를 남긴다. 새 쩜선 연결에도 메모와 재검토를 남긴다.
6. 연결된 Laya가 수정된 내용을 검토하고 판정·이유·시각을 저장한다. 검토 실패 시 내용은 보존하고 `failed`를 남긴다. 태그만으로 쩜을 삭제하거나 부족한 사실을 만들어 채우지 않는다.

기존 이름·별칭으로 확인한 동일 `jjumId`를 갱신한다. 모든 의미상 동일 대상의 자동 병합을 새로 구현한 것은 아니다. 초안의 `requestLayaReview:true`는 새 확정 발화의 근거가 있을 때 명시적 재검토 요청으로 수용한다. 내용 변경도 새 근거도 없는 반복 요청으로 검토를 계속 만들지 않는다.

검토 참고 문맥은 태그·이름·분류·요약·사실과 출처·사건으로 제한한다. `meta`, 전체 언급 이력, 내부 편집 이력과 통계는 표준 어댑터의 이 문맥에 포함하지 않는다. custom AIAdapter는 `ExtractRequest.recalledJJums`와 우선 참조 규칙을 직접 지원해야 한다. 전달 순서와 프롬프트 규칙이 실제 모델의 의미 판단 정확도를 보장하지는 않는다.

## 늦은 결과와 재시도

통합 처리는 내용·관계의 최종 저장을 마친 사용자 잠금 안에서 `captureLayaReviewIntent(storage,jjum,turns)`를 호출한다. 이 요청 객체는 저장 내용·대기 태그·발화 근거의 복사본을 내부 식별자에 묶는다. 잠금을 놓은 뒤 `reviewStoredJJum()`이 실행을 시작할 때 같은 저장 범위·쩜·내부 식별자와 내용·대기 태그가 여전히 일치하는지 확인한다. 다르면 이전 발화 근거로 검토를 시작하지 않는다.

`reviewStoredJJum()`은 AI 응답을 기다리는 동안 사용자 잠금을 놓으며, 결과를 저장할 때 다시 잠그고 최신 저장본을 읽는다. 이름·별칭·분류·요약·사실·사건·맥락·연결 대상/라벨 또는 대기 태그가 달라졌거나 작업이 무효화됐으면 이전 응답을 적용하지 않는다. 통계·언급 이력·서비스 확장 정보만 바뀐 경우는 내용 변경으로 보지 않는다. 다섯 번째 인자는 기존 발화 배열 또는 위 함수가 만든 `LayaReviewIntent`를 받는다. 별도 호출자가 저장 당시의 내용과 근거를 묶으려면 같은 저장 잠금 안에서 요청 객체를 만들어 전달해야 하며, 이를 직접 구성하거나 영구 저장하지 않는다.

내용을 같은 시각에 A→B→A로 되돌려도 어댑터의 변경 경로가 실행 전 요청과 진행 중 작업을 모두 무효화한다. 따라서 처음 A에 묶인 검토를 뒤늦게 시작하거나 그 응답을 잘못 적용하지 않는다. FileAdapter는 같은 프로세스의 같은 실제 저장 경로를 가리키는 여러 인스턴스가 `coordinationScope`를 공유하여 검토 중복과 이런 응답의 적용을 막는다. 다른 저장 어댑터는 공유 범위를 제공하거나 같은 객체를 사용한다. 이 식별 정보와 내용 비교값은 파일에 저장하지 않는다. 영구 검토 버전·해시·추가 검토 시각 필드는 없다.

같은 발화 ID를 재전송했을 때 완료 또는 실패 상태의 검토를 다시 실행하지 않는다. 내용 저장 후 검토 전에 중단된 `pending`은 편집 이력의 마지막 `reviewRequested`에 기록된 대화 ID가 일치하고, 그 근거 발화 ID 모두를 확정 발화로 포함한 요청에서만 재개한다. 예전 대화의 재전송으로 새 대화의 대기 검토를 시작하지 않는다. 이미 실행 중인 같은 검토는 중복 실행하지 않는다. 검토 결과만 저장한 재시도에서는 대화 결과의 `storedCount`가 0일 수 있다. 10,000개 단위의 연속 기록 묶음과 발화별 중복 방지는 기존 계약을 따른다.

FileAdapter의 직접 내용 수정도 판정을 대기로 바꾼다. 기존 편집 이력 뒤에 새 검토 요청이 추가되지 않은 직접 수정에는 `by:'batch'`, `action:'laya_review_invalidated'`, `reviewRequested:true`인 메모를 `evidence` 없이 덧붙인다. 이 대기는 재로드 후에도 옛 대화 재전송으로 재개하지 않으며 새 근거에 따른 요청이나 명시적 검토가 필요하고, 기존 미검토 파일을 읽기만 할 때는 기록을 추가하지 않는다. 검토 결과 저장에는 선택 계약인 `compareAndSetLayaTag(ownerId,jjumId,expectedSnapshot,expectedTag,newTag)`를 구현한다. 최신 파일의 내용과 대기 태그를 다시 비교한 뒤 태그만 바꾸며, 이 구간에는 다른 비동기 작업이 끼어들지 않는다. 검토 중 갱신된 통계·언급 기록·추가 필드도 최신 파일에서 보존한다.

다른 저장 어댑터로 직접 수정하는 호출자는 같은 무효화·대기 전환 계약을 지켜야 한다. 조건부 태그 저장을 지원하지 않으면 같은 사용자 잠금에 참여하는 쓰기 범위에서만 보호된다. 별도 프로세스·외부 파일 편집까지 원자적 비교 후 저장을 보장하지 않는다. 공유 조정에 참여하지 않는 쓰기 경로의 A→B→A를 영구 추적하지 않으므로 그런 쓰기는 호스트가 직렬화해야 한다. 여러 쩜을 한 번에 저장하는 트랜잭션이나 프로세스 간 잠금을 추가한 것은 아니다.

## Laya 연결

코어는 `LayaReviewEngine.reviewJJum({jjum,turns})`의 `{verdict,reason}` 결과를 받는다. 엔진이 없으면 `pending`을 유지한다. `LayaDecisionEngine`은 기존 회상 후보 재정렬과 함께 이 인터페이스를 구현한다.

Laya에 전달하는 쩜은 ID·이름·별칭·분류·태그·요약·사실과 시각/출처·사건·쩜선의 `targetId/label`로 제한하며, 검토 요청에 전달된 대화와 함께 판단한다. 연결 대상 쩜의 본문을 추가로 조회하지 않으며, 대상 ID만으로 정체나 관계를 추정하지 않도록 요청한다. 쩜선 굵기·`meta`·맥락 필드·통계·전체 언급 이력·내부 편집 이력은 이 입력에 포함하지 않는다.

로컬 서버에서는 기존 `HAEMA_LAYA_ENABLED=1`을 지정할 때만 연결한다. `HAEMA_LAYA_ENGINE_PATH`와 `HAEMA_LAYA_PYTHON_COMMAND`로 기존 Laya 환경 경로와 Python 실행 파일을 지정할 수 있다. `HAEMA_LAYA_MIN_CONFIDENCE`의 기본값은 0.70이다. 자동 설치·모델 다운로드는 이 기능에 포함하지 않는다.

Laya Router는 자유 문장을 생성하지 않는다. 검토마다 최대 세 번의 `choice` 질문으로 판정, 판정에 맞는 이유, 실제 입력에서 추린 원문 구절을 선택한다. 코어 연결부는 선택된 이유와 발췌 구절을 짧은 메모로 구성한다. 근거 후보는 요약 최대 하나·사실과 관계 라벨 합계 최대 세 개·전달된 대화의 마지막 네 개로, 합계 최대 여덟 개이며 각 발췌는 최대 120자다. 비어 있지 않은 관계 라벨을 배열 끝에서 최대 두 개 선택하고, 남는 자리를 사실 배열의 마지막 항목들로 채운다. 이 수량 제한은 메모에 인용할 발췌 후보에 적용하며, 앞서 설명한 검토 입력 전체를 여덟 구절로 줄이는 것은 아니다. 정상 판정인데 근거 구절을 선택하지 못하면 검토 실패로 처리한다.

신뢰도가 기준 미만이거나 유효하지 않은 선택·결과, 실행 오류·시간 초과는 `failed`다. **신뢰도 부족은 `정보 부족` 판정으로 치환하지 않는다.** 정보 부족도 유효한 선택과 판정 이유가 있는 검토 결과다. 외부 오류 원문에는 비공개 입력이 섞일 수 있으므로 `layaTag.reason`에는 일반적인 실패 메모만 저장한다. 회상 후보 재정렬 실패 시 기존 점수를 유지하는 정책과 이 검토 실패 상태는 구분한다.

엔진이 요청을 읽기 전에 종료하거나 입력 통신을 닫아도 연결부는 해당 호출의 실패로 전달한다. 자식 프로세스의 입력 오류를 처리되지 않은 이벤트로 남겨 서버 전체를 종료하지 않으며, 타이머를 정리하고 필요 없어진 프로세스에 종료를 요청한다. 이미 실패나 시간 초과로 끝난 호출에 늦게 도착한 종료·입력 오류로 결과를 다시 바꾸지 않는다. 이 처리는 정상 판정·자동 재검토·기억 삭제를 만들지 않는다.

## 검증 범위

검증은 모의 AI·Router 응답·합성 대화·임시 저장소로 수행한다. 최초 대기와 세 판정·이유 검증, 태그 우선 입력, 사실 출처 보존·업데이트 메모, 수정 후 재검토, 같은 시각의 내용 변경과 오래된 응답, 실패와 정보 부족의 구별, 같은 발화 재시도·대기 재개, 저장·재로드·기존 이력 호환을 확인한다. 기존 연속 기록·ID 중복 방지 회귀와 타입 검사도 함께 확인한다. 테스트와 로컬 서버는 저장소의 기존 방침대로 Git에서 제외된다.

입력 통신 오류의 회귀 검사는 실제 모델 대신 즉시 종료하거나 입력 통신을 닫는 합성 프로세스를 사용한다. 별도 Node 프로세스에서 검토·회상 호출을 실행해 오류가 호출자에게 전달되고 호출을 수행한 테스트 프로세스가 비정상 종료되지 않는지 확인한다. 정상 응답·시간 초과와 저장된 기억 보존도 별도로 구별한다.

실제 Laya 모델 실행과 한국어 판정 정확도, 실제 개인 기억, 유료 외부 AI 호출, 프론트 화면·receipt/ID 연동의 실행 검증은 이 범위에 포함하지 않는다. 보류 중인 회상 점수·언급 매너 계산식은 변경하지 않는다. 필드와 검증 계약은 [SCHEMA.md](SCHEMA.md), 발화 식별과 HTTP 계약은 [CONVERSATION_API.md](CONVERSATION_API.md)를 참고한다.
