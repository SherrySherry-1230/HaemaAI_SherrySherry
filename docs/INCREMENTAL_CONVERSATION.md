# 해마.ai 연속 입력과 증분 기억 처리

기획팀이 합의한 기준은 대화 맥락을 유지하면서 변경된 입력을 처리하고, 입력을 제출할 때마다 그 입력의 회상 점수 계산 상태를 초기화하는 것이다. 제출 단위는 의미상 완결된 발화 단위와 다르다. 이 문서는 백엔드 동작, 프론트엔드 연결 계약, 아직 결정하지 않은 호스트 전달 정책을 구분한다.

## 기존 경로와 달라지는 부분

기존 `POST /api/conversation`은 한 요청의 추출·저장·회상이 끝난 뒤 `hostPreview`를 반환한다. 발화 식별자와 저장 시 근거 검증은 있지만, 입력 중 스냅샷이나 제출 순간의 점수 무효화, 연속 입력 세션을 표현하는 경로는 아니다. 이 경로와 별칭인 `/api/conversation/process`, `/api/process`는 호환용으로 유지한다.

기존 콘솔의 `handleSend`는 `sending` 동안 다음 제출을 막으며, 한 번의 사용자 입력만 기존 경로에 전송한다. 500ms 타이머는 입력 표시를 제어하고, 별도 백그라운드 탐색은 실제 호출에 연결되어 있지 않다. Enter 처리에는 줄바꿈·한글 조합 확정과 제출을 구별하는 조건이 이미 있다. 이번 백엔드 작업은 이 화면 코드를 수정하지 않는다.

| 구분 | 연속 입력 경로의 기준 |
| --- | --- |
| 제출 수신 | 기억 처리 완료를 기다리지 않고 접수 결과를 반환하고 다음 제출을 받음 |
| 해석 근거 | 같은 세션의 실제 제출 원문과 현재 입력을 함께 사용 |
| 입력 중 탐색 | 변경된 스냅샷을 대상으로 준비하며 기본 탐색은 모델을 호출하거나 기억을 저장하지 않음 |
| 회상 점수 | 제출마다 이전 계산을 무효화하며 초기 상태는 미계산으로 표현 |
| 임시 후보 | 확정 쩜과 분리하고 다음 입력에서 검토한 뒤 폐기 |
| 비동기 결과 | 입력·스냅샷·작업의 유효성을 확인한 결과만 적용 |
| 재전송 | 같은 제출 식별자는 한 번 반영하고 같은 식별자의 다른 내용은 충돌로 거부 |
| 호스트 전달 | 응답 준비 권고를 제공하되 답변 실행은 호스트가 담당. 회상 결과 확정·전달 시점은 미선택 |

새 경로를 사용하는 클라이언트가 같은 제출을 기존 경로에도 동시에 보내면 안 된다. 기존 경로의 `hostPreview`를 새 경로의 자동 호스트 전달 정책으로 간주하지 않는다.

## 상태의 수명

| 상태 | 유지·종료 기준 | 구별해야 할 것 |
| --- | --- | --- |
| 대화 맥락 | 같은 세션의 다음 입력에도 실제 제출 원문을 유지 | 점수 초기화가 맥락 삭제를 의미하지 않음 |
| 입력별 회상 점수 | 제출 순간 이전 계산의 유효성을 끝내고 미계산으로 초기화 | 미계산은 모든 쩜을 관련 없음으로 판정한 0점이 아님 |
| 입력 중 임시 쩜 후보 | 확정 저장소와 분리. 제출 후 남은 조각은 다음 입력에서 검토 후 폐기 | 임시 후보의 생존이나 반복 검토가 확정 기억 승격 조건이 아님 |
| 확정 저장된 쩜 | 기존 기억의 보존·정정·삭제 원칙 유지 | 제출·임시 후보 폐기가 저장된 쩜·다른 점수·쩜선을 삭제하지 않음 |
| 실제 AI 사용량 | 실행된 해마.ai 호출을 별도 계량 계약으로 기록 | 결과가 오래되어 버려져도 실제 소비한 토큰은 취소되지 않음 |

0.5초는 **클라이언트가 입력 내용을 샘플링하는 간격**이다. 모델 호출 간격이나 전체 기억 처리의 반복 간격이 아니다. 현재 입력과 이전 스냅샷의 추가·삭제·수정을 비교하고, 변하지 않은 입력을 반복 처리하지 않는다. 기본 준비 탐색에서 얻은 예상 내용이나 임시 후보를 실제 사용자 발언으로 대화 이력에 넣지 않는다.

연속성 판단은 잠정 정보다. 문장 어미 등으로 이어질 가능성을 표시하더라도 하나의 의미 단위를 확정한 것으로 취급하지 않는다. 실제 제출 원문과 순서를 보존하며, 기억 추출에는 이어진 대화 맥락을 제공한다. 합성 사례에서 문맥이 전달된다는 검증과 실제 모델이 모든 분할 발화를 정확히 해석한다는 평가는 다르다.

기본 탐색기 `SpeculativeMemoryExplorer`는 현재 사용자의 활성 쩜을 다시 읽어 이름·별칭·쩜태그(JJ-tag)·상태를 확인한다. 이전 실제 맥락의 문자열 검색 위치를 재사용하되 편집 경계 주변과 새로 추가·변경된 검색어는 다시 검색한다. 이전 회상 점수는 재사용하지 않고 `recall({ touch: false, topicLimit: 0 })`로 매 작업 새로 계산한다. 여기의 0~1 점수는 기존 규칙 검색의 잠정 결과이며, 확정 회상 점수나 ‘직접 언급 5점’ 규칙을 대신하지 않는다.

입력 끝의 한글 접두어 두 음절 이상이 실제 저장 이름·별칭의 시작과 일치할 때만 완성된 이름을 `predicted` 탐색 후보로 준비한다. 새로운 사실이나 관계를 추정하지 않는다. 종결 문장부호가 없는 현재 입력을 `observed` 조각으로 남기는 것도 문장 구조에 따른 보수적 준비일 뿐 의미상 미완결 판정이 아니다. 탐색기는 읽기 전용 저장소 보기를 사용하며 모델·기억 쓰기·회상 통계 갱신·쩜선 변경을 실행하지 않는다.

## 세션·입력·작업 식별

코어의 `IncrementalConversationSession`은 `ownerId`, `storageId`, `conversationId` 범위를 고정하고 `sessionId`를 발급한다. 입력에는 아래 값을 전달한다. 같은 대화 ID라도 세션을 새로 만들면 기존 세션의 중복 처리 방지 기록을 공유하는 것으로 간주하지 않는다.

| 입력 필드 | 규칙 |
| --- | --- |
| `sessionId` | 서버가 발급한 현재 세션 식별자 |
| `inputId` | 제출할 입력의 안정적인 식별자. 입력 중 여러 스냅샷과 실제 제출에 같은 값 사용 |
| `sequence` | 1부터 시작하는 실제 제출 순서. 현재 `nextSequence`와 일치해야 함 |
| `revision` | 해당 입력 내용의 0 이상 정수 버전. 수정할 때 증가 |
| `text` | 실제 사용자 원문. 제출은 공백만인 내용을 허용하지 않음 |
| `at` | 선택적인 원래 입력 시각. 같은 입력의 재전송에 유지 |

접수 결과는 `{ accepted, replayed, stale, session }`다. `accepted`는 입력 상태에 반영했다는 뜻이며 기억 저장이나 호스트 답변 완료를 뜻하지 않는다. 같은 스냅샷 버전·내용·시각은 `replayed`로, 이미 제출한 입력의 스냅샷이나 낮은 스냅샷 버전은 `stale`로 구별한다. 같은 스냅샷 버전의 다른 내용, 다음 순서를 벗어난 입력은 충돌이다.

제출 재전송은 동일한 `inputId`, `sequence`, `text`, `at`인지 확인한다. 이미 접수한 제출의 재전송은 `revision`이 달라도 최초 값을 유지하며 새 작업을 시작하지 않는다. 같은 제출 ID로 내용이나 순서를 바꾸면 오류로 알린다. 클라이언트는 이미 제출한 내용의 수정이나 새 제출에 새 ID를 사용하고, 실패한 네트워크 요청의 재전송에 기존 ID를 유지한다. 아직 제출하지 않은 입력의 수정은 같은 `inputId`에서 `revision`을 올린다.

명시적인 처리 재시도는 제출 재전송과 구별한다. `retry(input, retryId)`는 가장 최근에 제출한 입력의 처리가 `failed`일 때만 새 처리를 시작한다. 같은 `retryId`의 재수신은 다시 실행하지 않으며, 같은 ID를 다른 입력에 쓰거나 진행 중·완료·과거 입력을 재시도하면 충돌이다. 재시도는 제출 개수·대화 원문·현재 회상 점수를 초기화하거나 추가하지 않고 `processGeneration`만 갱신한다. 실제 새 AI 호출의 사용량은 별도로 누적한다.

`session.turns`는 실제 원문과 순서를 보존한다. 입력 중 원문은 `final: false`, 실제 제출 원문은 `final: true`이며, 이 플래그는 저장 근거로 사용할 수 있는 실제 제출 여부를 나타낸다. 문장이 의미상 완결됐다는 판정이 아니다. `meaningUnitId`와 `continuity`는 잠정적인 연속성 묶음이다. `continuity.status`는 `likely` 또는 `undetermined`, `provisional`은 `true`이며 `precedingInputIds`와 판단 근거 `evidence`를 제공한다.

`analysisGeneration`은 입력 중 탐색 버전, `processGeneration`은 제출 후 처리 버전이다. 작업에는 `AbortSignal`과 `isCurrent()`를 전달한다. 다음 스냅샷·제출로 필요 없어진 탐색은 취소를 요청하고, 취소를 무시한 작업도 결과 적용 전에 현재 버전을 다시 검사한다. 입력 중 타이핑만으로 직전에 접수한 제출의 기억 처리를 취소하지는 않으며, 다음 실제 제출이 이전 제출의 미완료 처리를 대체한다.

| 조회 필드 | 의미 |
| --- | --- |
| `submissions[].processing.status` | `pending`, `completed`, `failed`, `superseded`. `completed`는 처리 함수 종료이며 결과 세부 상태를 함께 확인 |
| `recallScores.status` | `uncomputed`, `pending`, `ready`, `error` |
| `recallScores.values` | 미계산·실패에는 `null`. 계산 결과는 `{ jjumId, score }[]` |
| `recallScores.generation`, `inputId`, `revision` | 점수가 어떤 입력·버전의 것인지 구별 |
| `candidates` | 현재 입력에서 탐색한 임시 후보 |
| `carryoverFragments` | 다음 입력 한 번의 검토를 기다리는 이전 임시 후보 |
| `retrievedIds` | 현재 탐색에서 유효성을 확인한 쩜 식별자 |

임시 후보에는 `fragmentId`, `inputId`, `revision`, `generation`, `text`, `source`를 기록한다. `source: 'observed'`는 입력에서 관찰한 조각, `predicted`는 예상한 탐색 후보이며 어느 쪽도 확정 저장된 쩜이 아니다. 이전 임시 후보는 다음 비어 있지 않은 입력의 검토 함수가 실제 시작할 때 `previousFragments`로 한 번 전달하고 세션의 대기 목록에서 제거한다. 시작 전에 무효화된 작업은 후보를 소비하지 않으며, 검토 도중 오류나 취소가 발생해도 전달한 복제본을 확정 기억으로 돌려놓지 않는다. 스냅샷 없이 바로 다음 제출이 온 경우도 읽기 전용 탐색으로 검토한다. 내용이 나중에 실제로 확인되더라도 이전 객체를 승격시키지 않고 실제 제출 원문을 근거로 새 저장 판단을 한다.

저장 파이프라인은 `isCurrent` 검사와 `evidenceUtteranceIds` 근거 제한을 지원한다. 새 HTTP 경로는 이전 제출을 포함한 실제 대화 전체를 모델에 전달하되 `evidenceUtteranceIds: [work.inputId]`를 지정해 이번 제출의 유효한 확정 근거 ID를 포함한 초안만 저장 대상으로 인정한다. 과거 제출만 근거로 든 초안은 제외하지만, 이번 제출을 근거로 포함한 초안의 유효한 과거 근거도 함께 보존할 수 있다. 임시 후보 객체를 실제 발언으로 전달하거나 저장 대상으로 승격하지 않는다. 이 검사는 근거의 ID·역할·제출 상태를 확인하며, 초안의 모든 사실이 원문에 의해 의미적으로 입증되는지까지 보장하는 별도 판별기는 아니다.

늦은 추출·요약·검토 결과를 적용하기 전과 쩜 파일을 쓰기 전후에 유효성을 검사한다. 이미 완료된 쩜·쩜선 쓰기는 삭제하거나 되돌리지 않는다. 이 경계는 전체 다중 파일 작업의 원자적 롤백이 아니며, 사용자 정의 저장 어댑터 내부에서 이미 시작된 비동기 쓰기 자체를 강제로 취소하는 보장도 아니다.

## HTTP 접수·조회 계약

모든 새 경로는 선택한 기억 저장소와 `ownerId`, `conversationId`로 범위를 구분한다. `storageId`는 서버가 선택 저장소에서 계산하며 입력의 임의 값으로 저장소를 변경하지 않는다. 실제 경로를 응답에 노출하지 않는다.

| 요청 | 필수 값 | 성공 응답 |
| --- | --- | --- |
| `POST /api/conversation/session` | JSON의 `ownerId`, `conversationId` | 200 `{ success: true, session }`. 같은 범위의 살아 있는 세션은 재사용 |
| `GET /api/conversation/session` | 쿼리의 `ownerId`, `conversationId`, `sessionId` | 200 `{ success: true, session }` |
| `DELETE /api/conversation/session` | 쿼리의 `ownerId`, `conversationId`, `sessionId` | 200 `{ success: true, session }`. 작업 무효화·임시 상태 정리 후 `disposed: true` |
| `POST /api/conversation/snapshot` | JSON의 범위 값과 `sessionId`, `inputId`, `sequence`, `revision`, `text`, 선택적 `at` | 200 `{ success: true, accepted, replayed, stale, session }` |
| `POST /api/conversation/submit` | 스냅샷과 같은 입력 필드 | 새 제출 접수는 202, 동일 제출 재수신은 200. 응답 필드는 스냅샷과 같음 |
| `POST /api/conversation/retry` | 원래 제출의 범위·입력 필드와 안정적인 재시도 동작 ID `retryId` | 최신 실패 입력의 새 재시도 접수는 202, 같은 `retryId` 재수신은 200. 응답 필드는 스냅샷과 같음 |

예를 들어 입력 중 내용이 수정되고 실제로 제출되는 흐름은 다음과 같다. 식별자는 예시이며 실제 클라이언트가 발급·보존해야 한다.

```json
{
  "ownerId": "synthetic-owner",
  "conversationId": "synthetic-conversation",
  "sessionId": "서버가 발급한 세션 ID",
  "inputId": "synthetic-input-1",
  "sequence": 1,
  "revision": 2,
  "text": "이전 대화들을 참고할"
}
```

위 본문을 `/snapshot`에 전송한 뒤 같은 내용의 실제 제출은 `/submit`으로 전송한다. 다음 입력에는 새 `inputId`, `sequence: 2`를 사용하며, 새 입력의 내용 버전은 `revision: 0`부터 시작할 수 있다. 서버의 접수 응답을 기다리는 동안 입력 자체를 막지 말고 클라이언트 대기열에 원문과 순서를 보존한다. 네트워크 도착 순서가 뒤바뀌어 순서 충돌이 발생하면 최신 세션 상태를 확인하고 누락된 선행 제출부터 같은 ID로 재전송한다.

스냅샷 탐색과 세션 생성·조회에는 모델 설정이 필요하지 않다. 제출은 우선 접수하며 모델 설정이 없으면 비동기 `submissions[].processing.result`에 `success: false`, `code: 'AI_NOT_CONFIGURED'`를 남긴다. 설정을 완료한 뒤 같은 제출을 단순 재전송하면 기존 접수만 반환하므로 실제 재처리에는 `/retry`와 새 `retryId`를 사용한다. 성공적으로 처리한 제출의 `result`에는 `extraction`, `tokenUsage`, `conversationUsage`, `usagePersistence`, `hostHandoff`가 포함된다. 기억 처리 실패와 토큰 측정·보존 상태는 별도로 판단한다. 유효성을 잃은 제출은 `superseded`로 표시하며 실제로 소비한 토큰은 대화 사용량 조회에서 확인한다.

새 제출의 202 응답은 점수가 `uncomputed`, `values: null`로 초기화된 접수 사본이다. 처리 완료를 뜻하지 않는다. 클라이언트는 세션 GET에서 제출별 상태를 읽으며, 새 경로는 별도의 완료 이벤트 스트림을 제공하지 않는다. GET 폴링 간격을 500ms 입력 스냅샷 간격과 동일한 제품 규칙으로 해석하지 않는다.

| 오류 | 의미 |
| --- | --- |
| 400 `INVALID_INCREMENTAL_INPUT` | 필수 값·내용·버전 형식 오류 또는 조합 중 제출 등 |
| 409 `INPUT_CONFLICT` | 제출·스냅샷 식별자나 버전의 충돌, 다음 제출 순서 불일치 |
| 409 `SESSION_REQUIRED` | 현재 범위에 세션이 없거나 `sessionId`가 다름 |
| 409 `STORAGE_REQUIRED` | 선택된 기억 저장소가 없음 |
| 405 `METHOD_NOT_ALLOWED` | 해당 경로에서 지원하지 않는 HTTP 메서드 |
| 503 `SESSION_UNAVAILABLE` | 세션 처리에 필요한 서버 자원을 사용할 수 없음 |

세션의 원문·임시 후보·접수 중복 기록은 현재 서버 프로세스 메모리에 있다. 같은 프로세스에 재접속하면 현재 세션을 조회할 수 있지만, 서버 재시작이나 명시적인 세션 닫기 뒤에 이를 자동 복구하는 영구 세션 저장은 구현하지 않았다. 확정 쩜과 토큰 영구 기록은 별도로 보존된다. 새 세션에 과거 제출을 다시 보내면 새 모델 호출이 발생할 수 있으므로 세션 범위를 넘는 완전한 실행 중복 방지를 보장하지 않는다.

## 응답 준비 권고의 확정 기준

호스트 답변 시작 여부는 **입력 내용과 대화 흐름에서 의미상 마무리됐는지**를 기준으로 판단한다. 타이핑 여부와 경과 시간은 보조 신호이며 Enter 제출, 검색 완료, 일정 시간 경과 중 하나만으로 답변을 시작하지 않는다. 해마.ai는 입력 연속성과 응답 준비에 관한 권고를 제공하고, 실제 답변 실행은 호스트가 담당한다.

예를 들어 “오늘 친구를 만났는데” 다음 “전에 말했던 일 때문에 좀 어색했거든”은 이어질 맥락으로 다루고, “내가 먼저 연락해보는 게 좋을까?”처럼 요청이 드러났을 때 응답 가능을 권고하는 흐름이다. 이 권고와 회상 점수의 확정·전달은 별개다. 응답 가능을 권고했다고 아직 미정인 회상 전달 정책을 자동 선택하거나 호스트 답변을 실행하지 않는다.

서버가 반환하는 `session.responseReadiness`는 `assessResponseReadiness()`의 결과다. 현재 잠정 의미 묶음의 내용을 함께 보고, 이어지는 표현·열린 인용·명시적인 대기 요청에는 `wait`, 직접적인 요청·질문 표현에는 `ready`, 의미상 완료를 확인하지 못한 나머지는 `uncertain`을 권고한다. 인용된 질문은 직접 요청과 구별한다. 입력 중인 초안이 있거나 세션이 닫혔다면 `wait`다.

“다 말한 뒤에 설명해줘”처럼 요청에 대기 조건이 있으면 `wait`를 유지한다. 뒤의 질문만으로 그 조건을 해제하지 않으며 완료 또는 답변 허용 표현이 실제로 제출되어야 한다. 입력 중인 초안의 완료 표현만으로 대기를 해제하지 않는다. 이 구분도 제한된 표현 규칙이며 일반적인 조건 해석을 보장하지 않는다.

| 권고 필드 | 현재 계약 |
| --- | --- |
| `status` | `wait`, `ready`, `uncertain` |
| `source` | `content_heuristic`: 내용의 구조·표현에 따른 규칙 |
| `provisional` | 항상 `true`. 의미 판별이 확정됐다는 뜻이 아님 |
| `executeHost` | 항상 `false`. 호스트 답변을 실행하는 명령이 아님 |
| `basis` | `sessionId`, `processGeneration`, `analysisGeneration`, `inputIds`, 선택적 `meaningUnitId` |
| `reasons` | 어떤 내용 근거와 보조 제한을 적용했는지 나타내는 코드 배열 |

이 구현은 의미 판별 모델이 아니라 보수적인 내용 규칙이다. 문장부호 하나, Enter 횟수, 검색 완료, 시간만으로 `ready`가 되지 않으며, 말끝·인용·요청 표현만으로 구분하기 어려운 서술은 `uncertain`으로 남긴다. 문맥상 완결·말 끊김·숨은 요청을 일반적으로 판별하는 실제 모델 확장은 별도 구현안으로 남긴다. 호스트는 현재 세션·입력 버전과 맞는 권고만 참고하고, `ready`를 곧바로 확정 회상 결과나 답변 실행 승인으로 취급하지 않는다.

**미구현 확장 제안:** 의미 있는 새 제출이나 맥락 변경이 있을 때만 비동기 의미 판별기를 호출하고, 실제 대화 전체와 현재 입력을 주 근거로 제공한다. 타이핑 여부·경과 시간은 보조 정보로만 전달한다. 응답 형식을 `wait | ready | uncertain`과 근거 입력 ID·판단 이유로 제한하고 낮은 확신은 `uncertain`으로 남긴다. 같은 내용의 반복 스냅샷에는 모델을 호출하지 않으며, 세션·입력·작업 버전이 오래된 판정은 버린다. 이 모델 호출의 사용량은 해마.ai 계량에 포함하고, 호스트 실행은 계속 별도로 제어한다. 이 제안은 자동 적용하거나 모델·호출 비용 정책을 확정한 것이 아니다.

## 호스트 전달에 관한 미정 정책

처음 분리한 다섯 정책 중 답변 시작 판단의 기준은 위 내용·대화 흐름 기준으로 확정됐다. 나머지 시점·범위·중단 정책은 아래와 같이 제안하며 구현에서 자동 선택하지 않는다. 새 경로는 회상 결과의 호스트 전달을 `policy_pending`으로 구분한다. 이 값은 모든 기억의 관련성이 0이라는 뜻이 아니라, 확정 회상 결과의 전달 시점과 범위를 아직 정하지 않았다는 뜻이다.

| 미정 항목 | 제안 | 대안·결정할 조건 |
| --- | --- | --- |
| 1. 회상 점수 확정·호스트 전달 시점 | 제출한 입력의 불변 사본과 입력 ID·버전에 결합한 독립 결과를 만들어 전달 | 현재 입력창의 점수 상태와 전달 결과를 분리해야 다음 제출의 초기화가 이미 전달한 결과까지 지우지 않음 |
| 2. 제출 전 결과 사용 또는 제출 후 재산정 | **제출 → 이전 점수 무효화 → 확정 원문으로 새 회상 → 해당 입력 전용 결과 전달** 순서를 권장 | 제출 직전 스냅샷이 제출 원문·버전과 완전히 일치할 때만 결과를 동결한 뒤 초기화하는 대안이 있음. 지연은 줄지만 입력 직전 변경·누락·오래된 결과를 엄격히 검사해야 함 |
| 3. 호스트가 답변 중일 때 새 입력 처리 | 내용·대화 흐름에 따른 응답 준비 권고와 호스트 실행의 분리는 확정. 진행 중 답변에 새 입력이 오면 취소·수정·계속 중 어떤 방식을 사용할지 별도 결정 | 타이핑·시간은 보조 신호로만 사용. Enter·검색 완료·시간 경과만으로 답변 시작 금지 |
| 4. 다음 입력이 없을 때 임시 후보 정리 | 명시적인 세션 닫기 때 정리하는 경로를 제공하고 자동 만료 시간은 별도 결정 | 유휴 시간 기준의 만료를 추가하려면 기간과 재접속 시 동작을 합의해야 함 |
| 5. 직접 언급한 쩜 5점의 적용 범위 | 마지막 제출 원문만 적용하거나 확인된 의미상 발화 묶음 전체에 적용하는 방안을 비교 | 잠정 연속성 묶음을 확정 의미 단위처럼 취급하지 않음. 범위가 정해지기 전 전체 대화에 5점을 확대 적용하지 않음 |

첫 두 제안은 같은 순서의 설계안이다. 제출 시 초기화는 **이전 입력창 계산 상태**를 끝내는 일이고, 호스트 전달은 **특정 제출을 대상으로 완성한 결과**를 내보내는 일이다. 두 상태를 분리하면 초기화 때문에 유효한 결과를 한 번도 전달하지 못하는 구조를 피할 수 있다. 현재 구현은 이 권고안을 제품 정책으로 확정하지 않는다.

## 프론트엔드 인계

화면·스타일 변경과 실제 호스트 답변 제어는 별도 작업이다. 다음 항목을 새 경로에 연결해야 사용자가 실제 화면에서 연속 입력할 수 있다.

1. 요청 하나가 진행 중이라는 이유로 입력창이나 다음 제출을 잠그지 않는다. 접수 상태와 비동기 기억 처리 상태를 구분한다.
2. 하나의 세션에서 안정적인 제출 식별자와 순서를 생성하고, 네트워크 재전송에 같은 값을 사용한다. 내용이 같다는 이유만으로 서로 다른 실제 제출을 합치지 않는다.
3. 500ms마다 현재 내용을 샘플링하되 변경이 없으면 새 탐색을 요구하지 않는다. 줄바꿈이나 한글 입력 조합 확정을 제출로 보내지 않고, 실제 제출 이벤트만 제출 경로에 보낸다.
4. 제출 직후 다음 입력을 받을 수 있게 하고 이전 입력의 회상 표시를 미계산으로 전환한다. 오래된 비동기 응답이 현재 입력을 지우거나 최신 결과를 덮어쓰지 않게 식별자와 버전을 검사한다.
5. 입력 중 임시 후보, 확정 쩜, 미계산 점수, 계산 결과, `policy_pending`을 구별한다. 0점·빈 검색·초기화·오류를 같은 상태로 표시하지 않는다.
6. `responseReadiness`를 내용에 근거한 잠정 권고로 읽고 답변 실행은 호스트에서 제어한다. 회상 결과는 별도 전달 정책을 선택한 뒤 연결하며 `policy_pending`을 확정 회상 결과로 취급하지 않는다. 답변 도중 새 입력을 받았을 때 취소·수정·계속 여부도 별도로 정한다.
7. 처리 실패에 대한 명시적 재시도는 `/retry`와 안정적인 `retryId`를 사용한다. 단순 네트워크 재전송과 새 처리 실행을 분리한다. 토큰은 [토큰 계량 계약](TOKEN_USAGE.md)에 따라 실제 해마.ai 호출만 누적하고, 오래된 작업의 실제 소비도 누락하지 않는다.

## 검증과 한계

검증에는 합성 대화·합성 저장소·가짜 모델 응답을 사용한다. 실제 API의 의미 해석 품질, 브라우저 입력 동작, 한글 조합 이벤트의 실제 기기 동작, 호스트 답변 생성은 백엔드 단위·HTTP 검사만으로 검증 완료라 하지 않는다. 각 실행 결과와 남은 한계는 `HISTORY.md`에 기록한다.

| 확인할 사례 | 기대 결과 |
| --- | --- |
| “이전 대화들을 참고할” → “수는 있음. 같은 섹션의 이전 대화들을 유저가 대화를 여러 번에” → “나누어 끊어치는 경우 맥락이 이어져야지.” | 세 제출의 순서와 원문이 유지되고 뒤의 처리에 앞선 맥락이 전달됨. 제출마다 이전 회상 점수는 무효화됨 |
| 입력 중 같은 스냅샷 반복 | 불필요한 모델 호출·기억 저장·동일 탐색을 반복하지 않음 |
| 입력의 일부 추가·삭제·수정 | 변경 범위와 필요한 이전 맥락을 대상으로 새 작업 준비 |
| 제출 직전에 시작한 느린 탐색이 제출 후 완료 | 이전 점수나 임시 후보를 현재 상태에 적용하지 않음 |
| 다음 제출이 먼저 접수되고 이전 추출이 늦게 완료 | 오래된 작업의 확정 저장을 막고 최신 작업은 이어진 실제 맥락으로 판단 |
| 이전 입력에서 남긴 임시 후보 | 다음 입력 처리 때 검토 후 폐기. 후보만으로 확정 쩜을 생성하지 않음 |
| 같은 제출의 재전송 | 같은 입력이 중복 반영되거나 쩜 생성 작업이 중복 시작되지 않음 |
| 최신 실패 제출의 명시적 재시도 | 문맥·제출 수·현재 회상 점수는 유지하고 처리만 재실행. 같은 `retryId` 재수신은 추가 호출 없음 |
