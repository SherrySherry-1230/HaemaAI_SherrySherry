# 해마.ai 토큰 사용량 계약 v2

해마.ai가 실행한 AI 호출의 토큰 사용량을 제공자 응답에서 수집하고 서버에 보존한다. `tokenUsage`는 이번 처리의 증가량이며 `conversationUsage`는 같은 저장소·사용자·대화의 누적량이다. 프론트엔드는 두 수치로 발화별 증가량과 하나의 대화 누적 막대를 표시한다.

기획팀이 정한 표시는 **이번 증가량 / 대화 누적량**이다. 예를 들어 이번 처리에서 13토큰을 사용했고 누적량이 150토큰이면 `+13 / 150`을 표시한다. 막대는 입력·출력을 색으로 구분하고 이번 증가 부분을 진하게 표현한다. 합계만 알려진 미분류 사용량은 별도 중립 표시를 사용한다. 화면·벡터 구현은 프론트엔드가 담당한다.

## 식별 범위와 처리 상태

처리별 `tokenUsage` 보고서는 `schemaVersion: 2`, `scope: 'haema'`, `unit: 'tokens'`를 명시한다. 누적을 구별하는 신원은 `ownerId`, `storageId`, `conversationId`의 조합이다. 서로 다른 사용자나 저장소의 대화 ID가 같아도 합치지 않는다. 제공자·모델을 바꾸어도 동일한 대화의 이전 사용량은 기록된 값으로 보존하며 재환산하거나 삭제하지 않는다.

한 번의 처리마다 새 `usageId`, 각각의 실제 AI 호출마다 새 `callId`를 사용한다. `utteranceIds`는 그 처리에 포함된 발화 식별자를 나타낸다. 한 발화의 처리는 `single`, 여러 발화를 함께 처리하면 `shared`로 귀속을 구분한다. 공동 호출의 소비량을 발화 수만큼 복제하거나 글자 수 비율로 나누지 않는다.

`phase: 'pending'`은 진행 중, `phase: 'complete'`는 처리 종료를 나타낸다. 처리 종료는 사용량이 모두 알려졌다는 뜻이 아니며 성공 응답만을 뜻하지도 않는다. 실패한 호출이나 사용량을 제공하지 않는 모델이 있어도 처리는 종료될 수 있다.

## 합계와 입력·출력 구성은 별도로 판단

`totalStatus`와 `breakdownStatus`는 각각 `complete`, `partial`, `unreported` 중 하나다. 합계 확인 여부와 입력·출력 구분 여부를 같은 상태로 취급하지 않는다. `status`는 호환용으로 제공하는 `totalStatus`의 별칭이다.

| 받은 사용량 | 전체 합계 | 합계 상태 | 표시 원칙 |
| --- | --- | --- | --- |
| 입력 5, 출력 8, 합계 13 | 13 | `complete` | 입력 5와 출력 8을 구분 |
| 합계 13만 제공 | 13 | `complete` | 13을 미분류로 표시; 입력·출력은 만들지 않음 |
| 입력 5만 제공 | `null` | `partial` | 확인된 부분 5를 사용해 `5 이상` 표시 |
| 모두 미제공 | `null` | `unreported` | 미제공으로 표시; 0으로 대체하지 않음 |
| AI 호출 없음 | 0 | `complete` | 실제 0으로 표시 |

`totalTokens`는 완전한 전체 합계이며 일부 호출의 합계가 확인되지 않으면 `null`이다. `reportedTotalTokens`는 확인된 부분의 합계다. 호출별 전체 합계가 있으면 그 값을 사용하고, 전체를 모르면 확인된 입력·출력 부분만 더한다. 부분 합계를 완전한 전체 수치처럼 표시하지 않는다.

막대의 구성은 알려진 입력, 알려진 출력, 미분류 토큰으로 구별한다. 합계만 제공된 13토큰은 합계가 확실하므로 전체량 13을 유지하고 미분류 부분에 놓는다. 입력 5만 제공된 경우에는 전체량을 알 수 없으므로 5를 하한으로 표시한다. `null`은 미제공이고 0은 확인된 값이다.

| 필드 | 의미 |
| --- | --- |
| `inputTokens`, `outputTokens` | 각각의 전체 합계. 해당 구분에 누락된 사용량이 있으면 `null` |
| `unclassifiedTokens` | 전체 합계에서 알려진 입력·출력을 제외한 양. 전체를 확정할 수 없으면 `null` |
| `segments.input`, `segments.output`, `segments.unclassified` | 막대에 놓을 수 있는 확인된 각 구간의 합계 |
| `callCount` | 관측한 AI 호출 수 |
| `unreportedCallCount` | 입력·출력·합계가 모두 미제공인 호출 수 |
| `incompleteCallCount` | 입력·출력·합계 중 하나라도 미제공인 호출 수 |
| `calls` | 호출별 출처와 사용량 기록 |
| `byTask`, `byModel` | 작업별 및 모델 출처별 집계 배열 |

`segments`의 0은 그 구간에서 확인된 소비가 없다는 뜻이며 미확인 소비까지 0이라고 확정하는 값이 아니다. 미제공 상태를 먼저 확인하고 막대를 표시한다. 합계 13만 제공된 완료 처리의 일부 필드는 다음과 같다.

```json
{
  "schemaVersion": 2,
  "scope": "haema",
  "unit": "tokens",
  "phase": "complete",
  "coverage": "complete",
  "status": "complete",
  "totalStatus": "complete",
  "breakdownStatus": "unreported",
  "inputTokens": null,
  "outputTokens": null,
  "totalTokens": 13,
  "reportedTotalTokens": 13,
  "unclassifiedTokens": 13,
  "segments": { "input": 0, "output": 0, "unclassified": 13 }
}
```

이는 필드 설명용 발췌이며 실제 보고서는 신원·발화 식별자·호출 내역도 함께 제공한다. `sections`는 작업별 진단에 남기는 보조 집계다. 프론트엔드의 주 계량기는 `segments`를 사용하는 하나의 누적 막대다.

처리 보고서의 `coverage`는 `totalStatus: 'complete'`이며 `phase: 'complete'`일 때만 `complete`다. 합계가 완전하고 입력·출력 구성만 모르는 보고서를 전체 미제공으로 낮추지 않는다. 반대로 진행 중에 알려진 수치가 있다고 최종 합계로 확정하지 않는다.

제공자별 캐시·추론 세부값은 입력·출력에 포함되는 방식을 확인하여 정규화하며 이미 포함된 값을 다시 더하지 않는다. 잘못되거나 서로 모순되는 값은 전체 사용량으로 인증하지 않는다. 안전한 정수 범위를 넘은 누적값은 정확한 숫자로 표시하지 않는다.

## HTTP 응답과 재접속 복원

`GET /api/storage/status`는 현재 선택한 저장소의 `storageId`를 제공한다. 연결되어 있으면 사용량 보고서와 같은 불투명 식별자이며, 미연결이면 `connected: false`, `storageId: null`이다. `POST /api/storage/init`도 실제 연결을 마친 `connected: true` 응답에 같은 식별자를 제공한다. 기존 저장소의 존재만 알리는 `exists: true` 응답은 연결 완료가 아니므로 신원을 바꾸는 근거로 사용하지 않는다.

식별자는 기존 장부와 동일하게 실제 경로를 해석한 뒤 계산한다. 같은 저장소를 심볼릭 링크로 연결해도 같고, 다른 실제 저장소로 전환하면 달라진다. 원래 저장소 재연결과 서버 재시작은 식별자를 바꾸지 않는다. 식별자를 조회하기 위해 사용량 장부나 새 저장소를 만들지 않는다. 프론트엔드는 조회·처리 요청을 시작할 때의 `storageId`를 보존하여 첫 사용량 응답부터 대조하고, 저장소 전환 이후 도착한 이전 요청을 현재 선택에 적용하지 않아야 한다. 기존 `storageRoot`는 경로 표시·호환용이며 사용량 신원 대조에는 `storageId`를 사용한다.

`POST /api/conversation`의 사용량 측정이 시작된 처리에는 다음 두 보고서를 연결한다. 실패 응답도 이미 소비한 토큰을 포함할 수 있으므로 오류 처리 전에 사용량을 읽는다. 입력 검증·설정 확인 등 실행 전 실패에는 측정 보고서가 없을 수 있다.

| 응답 필드 | 용도 |
| --- | --- |
| `tokenUsage` | 이번 처리 한 번의 증가량. `usageId`로 같은 처리의 재수신을 구별 |
| `conversationUsage` | 서버에 보존된 같은 저장소·사용자·대화의 전체 누적량 |
| `usagePersistence.status` | `saved`이면 누적 저장·읽기 확인 완료, `failed`이면 보존 확인 실패 |

프론트엔드는 새 누적 응답을 기존 누적량에 다시 더하지 않는다. `tokenUsage`로 이번 증가량을 표시하고, 전체량은 `conversationUsage`를 기준으로 갱신한다. POST 응답을 반복 수신하거나 다시 그려도 동일한 소비가 중복 증가하지 않아야 한다.

누적 보고서 `conversationUsage`도 `schemaVersion: 2`, `scope: 'haema'`, `unit: 'tokens'`와 세 신원 필드를 제공하며, 사용량 집계 외에 다음 필드를 포함한다. 처리별 `phase`·`coverage`는 누적 객체 자체에 복제하지 않는다. 누적의 진행 상태는 `pendingUsageIds`와 `totalStatus`로 판단한다.

| 누적 필드 | 의미 |
| --- | --- |
| `found` | 해당 대화의 서버 기록이 존재하는지 여부 |
| `revision` | 서버 기록이 변경될 때 증가하는 버전. 동일 결과의 재저장은 증가하지 않음 |
| `reports` | 보존된 처리별 보고서 배열 |
| `usageIds`, `reportCount` | 포함된 처리 식별자와 수 |
| `pendingUsageIds` | 아직 완료되지 않은 처리 식별자 |

같은 신원의 늦은 응답이 도착하면 `revision`을 확인하여 더 오래된 누적으로 화면을 되돌리지 않는다. `usagePersistence.status: 'failed'`일 때 `conversationUsage`는 `null`이다. 이번 측정값을 잃지 않도록 유지하되, 실패한 저장을 서버 누적에 반영된 것으로 표시하지 않는다.

재접속 후에는 다음 읽기 전용 경로로 누적량을 복원한다.

```http
GET /api/conversation/usage?ownerId=synthetic-owner&conversationId=synthetic-conversation
```

조회는 요청을 시작할 때 선택된 저장소 범위에 고정한다. 실제 ID는 쿼리 문자열에 넣기 전에 URL 인코딩한다. 프론트엔드는 현재 선택한 저장소·사용자·대화와 반환된 식별자가 일치하는 결과만 표시한다. 다른 화면의 늦은 응답으로 현재 막대를 바꾸지 않는다.

GET 성공 응답은 `{ success: true, conversationUsage }`다. 기록이 없으면 `found: false`, `revision: 0`, 빈 `reports`와 집계의 초기값을 반환한다. 이는 과거 실제 소비가 0이었다는 인증이 아니라 보관된 계량 기록이 없다는 뜻이다. 읽기·검증 실패는 HTTP 503과 `{ success: false, code: 'TOKEN_USAGE_STORAGE', conversationUsage: null }`로 알리며, 기존 기록을 0으로 바꾸지 않는다. 잘못된 조회 신원은 400 `INVALID_USAGE_SCOPE`, 선택된 저장소가 없으면 409 `STORAGE_REQUIRED`다. 이 읽기 경로는 AI 설정이나 모델 실행을 요구하지 않는다.

서버 영구 기록을 대화 누적의 기준으로 사용한다. 브라우저의 임시 보관만으로 누적을 유지하거나 새로고침 때 0부터 시작하는 방식으로 대체하지 않는다. 기존 `receipt`는 발화 식별과 재시도에 사용하는 계약이며 사용량 ID를 대체하지 않는다.

## 프론트엔드 수신부 수정·검증 기준

기존 수신기의 단독 검증 통과는 이 v2 계약의 연결 완료를 뜻하지 않는다. 아래 항목은 수신부가 실제 POST 응답과 재접속 GET 응답을 처리할 때 확인할 인수 기준이다. 문서 작성이나 백엔드 검증만으로 화면 연결이 완료됐다고 표시하지 않는다.

| 입력·상황 | 기대 결과 |
| --- | --- |
| 완료 호출이 입력 5만 제공 | `totalTokens: null`, `reportedTotalTokens: 5`, `totalStatus: 'partial'`, `segments.input: 5`를 보존하고 `5 이상` 표시. 합계 미제공이라는 이유로 알려진 입력을 버리지 않음 |
| 완료 호출이 합계 13만 제공 | `totalTokens: 13`, `totalStatus: 'complete'`, `coverage: 'complete'`, `breakdownStatus: 'unreported'`, 미분류 13. 구성 미제공을 전체량 미확정으로 취급하지 않음 |
| 완료된 `usageId`에 합계 7을 받은 뒤 같은 ID로 다른 호출 목록·합계 11 수신 | 변경 결과를 충돌로 거부하고 기존 7 유지. 두 목록을 합쳐 18로 만들지 않음 |
| 같은 완료 보고서를 반복 수신 | 증가량·누적량을 다시 더하지 않음 |
| 처리 실패 응답이 완전한 사용량 7을 제공 | 처리 오류는 표시하되 사용량은 7의 `complete` 유지. HTTP 실패만으로 `partial`로 바꾸지 않음 |
| 위 실패 뒤 실제 재시도가 새 `usageId`·새 `callId`로 완전한 사용량 11을 제공 | 보존된 두 처리의 누적량은 18. 두 보고서가 완료됐고 모든 소비량이 알려졌다면 누적도 `complete` |
| 위 재시도 중 어느 호출이 사용량 미제공 | 알려진 부분은 보존하되 전체량은 `null`. 재시도 성공으로 앞선 미제공 소비까지 확정하지 않음 |
| 다른 `usageId`가 이전 `callId` 재사용 | 충돌로 거부. 같은 실제 호출을 새 처리로 중복 등록하지 않음 |
| 진행 중 보고서가 같은 ID의 정상 완료 보고서로 갱신 | 동일 처리의 상태 갱신으로 반영. 완료 전후의 중간 합계를 각각 추가하지 않음 |
| POST 응답이 이번 13·서버 누적 150 제공 | 이번 증가량은 `+13`, 전체는 150. 기존 누적에 150을 다시 더하지 않음 |
| 새로고침·브라우저 재접속·서버 재시작 | 같은 신원으로 GET하여 서버 기록 복원. `sessionStorage`에 기록이 없어도 서버 누적은 유지 |
| 기록 없는 조회 또는 저장·조회 오류 | `found: false`와 오류를 구별하고 기존 소비를 실제 0으로 초기화하지 않음 |
| 다른 저장소·사용자·대화 응답 또는 낮은 `revision`의 늦은 응답 | 현재 신원의 더 최신 누적을 덮어쓰지 않음 |

수신부 연결은 다음 순서로 확인한다.

1. 응답의 `schemaVersion`, `scope`, `unit`과 저장소·사용자·대화 신원을 검증한다. 여러 발화의 공동 처리는 같은 사용량을 복제하지 않는다.
2. 성공·실패 응답 모두에서 `tokenUsage`와 `conversationUsage`를 읽는다. 처리 오류를 던지거나 실패 상태로 전환하기 전에 알려진 사용량을 보존한다.
3. 처리 성공 여부, `phase`, `totalStatus`, `breakdownStatus`, `usagePersistence.status`를 각각 사용한다. 하나의 성공·실패 플래그로 사용량 상태를 덮어쓰지 않는다.
4. 완료된 `usageId`의 원본과 호출 목록을 보존하고 같은 ID의 변경 결과를 거부한다. 진행 중에서 완료로의 정상 갱신과 새 ID의 실제 재시도를 구분한다.
5. 증가량은 처리 보고서에서, 대화 전체량은 서버 누적에서 읽는다. 재접속 때 GET으로 복원하며 브라우저 저장은 임시 보관으로만 사용한다.

## 서버 보존 범위

`FileTokenUsageStore`는 선택된 기억 저장소의 `.🫀해마_심층_중추신경계🫀/token-usage/` 아래에 사용자·대화별 기록을 보존한다. 하위 파일명은 사용자·대화 ID의 해시이며 `storageId`는 실제 저장소 경로의 해시로 만든 식별자다. 사용량 보고서에는 실제 경로를 넣지 않는다. 저장 파일에는 보고서의 식별자·모델 출처·사용량을 보존하고 원문·프롬프트·API 키를 보존하지 않는다.

서버는 AI 호출 전에 진행 중 기록을 먼저 저장한다. 이 최초 저장이 실패하면 503 `TOKEN_USAGE_STORAGE`를 반환하고 새 AI 소비를 시작하지 않는다. 호출 시작·완료마다 진행 상태를 갱신하며, 중간 기록 쓰기가 실패하면 처리 종료 때 다시 저장을 시도한다. 마지막 저장·조회 확인 결과는 `usagePersistence.status`로 알린다. 기억 처리 성공 여부와 사용량 영구 보존 여부를 별도로 확인해야 한다.

파일 쓰기는 임시 파일을 작성·동기화한 뒤 교체하며 동시 쓰기 잠금으로 충돌을 감지한다. 손상된 기록, 서로 다른 신원의 기록, 상충하는 사용량이나 해소되지 않은 잠금은 오류로 알리고 기존 원본을 임의 초기화하지 않는다. 종료 전에 서버에 기록된 결과는 재시작·재접속 후 조회할 수 있다. 서버가 소비한 모든 호출의 완료 기록까지 저장하기 전에 중단되었다면 진행 중 상태나 미제공 값을 유지하며 모르는 소비량을 채우지 않는다.

## 중복·재시도·진행 중 기록

같은 `usageId`의 같은 결과를 다시 저장하거나 수신하는 것은 한 번의 처리다. 진행 중 기록은 같은 처리의 완료 기록으로 갱신할 수 있다. 완료된 호출 이벤트와 결과를 나중에 다른 숫자로 덮어쓰지 않는다.

호출 이벤트의 진행 상태는 `state`, 처리 보고서의 진행 상태는 `phase`로 구분한다. 호출 시작 시 `state: 'pending'`과 미제공 수치를 기록하고, 같은 `callId`의 `complete` 이벤트로 완료한다. 하나의 처리가 여러 AI 호출을 실행하는 동안은 보고서가 `pending`일 수 있다. 완료 이벤트를 진행 중으로 되돌리거나 관측한 호출을 보고서에서 제거할 수 없다.

다른 `usageId`에서 이미 쓰인 `callId`를 다시 사용하는 것은 충돌이다. 실제 AI 재실행은 새 `usageId`와 `callId`를 발급하고 추가 소비로 누적한다. 같은 발화 ID를 유지한 재시도도 토큰을 실제 소비했다면 추가한다. 기억을 중복 저장하지 않는 것과 사용량을 누적하는 것은 별개의 동작이다.

응답이 유실되었어도 서버에 기록된 사용량은 조회로 복원한다. 기록되지 않은 과거 호출이나 제공자가 보고하지 않은 소비를 만들어 채우지 않는다. 진행 중 중단된 처리와 사용량 미제공 기록도 남겨 전체가 확인된 것처럼 표시하지 않는다.

코어의 `summarizeTokenUsage(events)`는 같은 호출의 중복 이벤트를 한 번만 합산한다. `summarizeConversationTokenUsage(reports, expectedScope?)`는 저장소·사용자·대화 신원을 확인하고 보고서를 합산한다. 누적 결과에는 `usageIds`, `reportCount`, 진행 중 보고서의 `pendingUsageIds`와 사용량 집계가 포함된다. 진행 중 보고서가 남으면 알려진 부분을 보존하면서 최종 `totalTokens`를 `null`로 유지한다. 같은 호출이나 처리 ID에 상충하는 결과가 있으면 조용히 덮어쓰지 않고 오류로 알린다.

## 호출 수집과 측정 범위

사용량은 AI 응답 내용을 JSON으로 해석하기 전에 수집한다. 내용 해석이나 이후 저장이 실패해도 제공자 응답으로 확인한 소비량을 버리지 않는다. 호출 기록에는 `callId`, 제공자·모델·작업 종류와 사용량을 남기고 발화 원문·프롬프트·API 키를 넣지 않는다.

| 호출 필드 | 의미 |
| --- | --- |
| `scope` | `haema` |
| `provider`, `requestedModel` | 호출 당시의 제공자와 요청 모델 |
| `model`, `modelSource` | 응답이 알려 준 모델이면 `response`; 모델명이 없으면 요청 모델과 `requested` |
| `task` | `extract`, `summarize`, `judgeMerge`, `scoreRecall`, `review` |
| `source` | 확인된 수치를 제공받은 `provider` 또는 모두 미제공인 `unreported` |
| `usageSource` | `openai.usage`, `anthropic.usage`, `google.usageMetadata`, `ollama.counts` 또는 `null` |
| `inputTokens`, `outputTokens`, `totalTokens` | 제공자 응답에서 정규화한 수치 또는 미제공 `null` |

`modelSource: 'requested'`인 모델을 실제 응답 모델이 확인된 것으로 표시하지 않는다. `byModel`은 제공자·모델·모델 출처를 함께 구분한다. OpenAI 호환 사용량이 없는 Ollama 응답은 실제 반환된 `prompt_eval_count`, `eval_count`를 확인해 수집하며 시간이나 문자열 길이를 토큰으로 바꾸지 않는다.

입력 토큰은 사용자 원문만의 길이가 아니다. 시스템 지시, 이전 발화, 기존 기억과 작업별 입력이 포함된다. 같은 문맥을 여러 번 읽히면 실제 호출에서 보고된 횟수만큼 소비에 포함된다. 모든 AI가 동일한 방식으로 문장을 토큰으로 나누지는 않으므로 서로 다른 모델의 합계는 보고된 개수의 합이다. 같은 처리량이나 가격을 의미하지 않는다.

일반 회상은 기억을 규칙으로 검색하므로 AI 토큰을 소비하지 않는다. 선택적 Laya 검토·회상 엔진이 실제로 실행되어도 현재 경로는 사용량을 제공하지 않으므로 미제공 호출로 기록한다. 엔진이 설정되어 있어도 실행되지 않았다면 미제공 호출을 추가하지 않는다.

`recall.stats.tokensUsed`와 후보의 `tokens`는 전달할 기억 문장의 길이에 대한 추정치이므로 실제 소비량에 합산하지 않는다. 이 계약은 해마.ai가 측정한 호출만 다루며 호스트 AI 답변의 사용량은 포함하지 않는다.

OpenAI·Anthropic·Groq SDK는 `maxRetries: 0`으로 자동 재시도를 끈다. 현재 설치된 Google SDK의 요청 경로도 네트워크 요청을 한 번 실행하는 것을 확인했다. 다시 호출할 때는 별도 실제 호출로 관측하며 추가 소비로 기록한다. 제공자 내부 처리 등 응답에 보고되지 않은 소비까지 복원하지는 않는다. 보고된 토큰 수만으로 비용이나 과거 대비 절감률을 확정하지 않는다.
