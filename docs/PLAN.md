## 선택적 Laya 판단층

`engines/laya`의 Laya는 쩜 원문 생성기가 아니라 회상 후보를 빠르게 점수화하는 보조 판단 엔진으로 사용한다.
기본값은 꺼져 있으며, 로컬 서버 실행 시 `HAEMA_LAYA_ENABLED=1`을 지정한 경우에만 활성화된다.
Laya 모델 로딩 실패, 실행 오류, 또는 confidence가 기준(기본 0.70)보다 낮은 결과는 기존 결정론적 회상 점수를 유지한다.
첫 적용 범위는 회상 후보 재정렬이며, 쩜 생성·요약·최종 병합은 기존 AI 어댑터와 코어가 담당한다.


## AI 어댑터 — 설계 원칙 (2026-09-04 확정)

**Haema는 AI를 직접 호출한다. 단, 역할은 "점을 만드는 것"까지.**

- 하는 일: ① 대화에서 쩜 추출 ② summary·관계 요약 생성 ③ 병합 후보 판정 ④ 회상 후보 점수화
- 안 하는 일: **유저에게 말하기** (말투·연출·꺼낼지 침묵할지 = 호스트 챗봇 몫) / **기억 지어내기**
- 주입: 개발자가 provider(`"anthropic" | "openai" | "google" | custom`) + model + apiKey 주입.
  **Haema는 키를 저장·로깅하지 않는다** (호출 시 메모리 보관만).
- 레퍼런스 구현 3종 + 커스텀 함수 주입. **작업별 모델 분리 가능** (추출용/판정용 따로 지정).
- 프롬프트는 범용. 서비스 특화 지시는 호스트가 **hint 문자열**로 넘기고, Haema는 hint를
  해석하지 않는다 — 프롬프트에 그대로 전달할 뿐 (도메인 무지 유지).
- 인터페이스: `src/adapters/aiAdapter.ts`와 provider 어댑터 구현체(2단계)

- **테스트 콘솔(CLI)**: 쩜 생성/조회/자극/선/회상 후보 미리보기 — **AI 호출 없이** 손 조작용

## 2단계 — 회상 (Recall): 선별 주입 엔진 (설계 확정 2026-09-05 · **2-a 완료 2026-09-06**)

> 두 덩이로 나눠 구현: **2-a 회상 엔진(AI 없이 결정론)** — `src/recall.ts` · `src/proactive.ts` · `src/valence.ts` 완료 /
> **AI 어댑터**(extract·summarize·judgeMerge·score) — 인터페이스 + 레퍼런스 구현(OpenAI SDK 호환
> Upstage Solar Adapter)까지 완료. 단, **기본 대화→추출→쩜 생성→요약→저장 파이프라인은 `src/integration.ts`에 조립되어 있다.**
> 다만 추출 결과의 병합·선 연결 고도화와 마이풉 연동은 아직 남아 있으며, 마이풉 연동은 아직 착수하지 않았다.
> 마이풉↔Haema 연동은 마이풉에 직접 붙이기 전에 임시 웹콘솔(로컬 HTML)로 먼저 돌려보고,
> 그다음 정식 연동하는 순서로 진행한다.

**출력 구조 — 점만 주지 않는다. 매 턴 3종을 반환한다:**

| # | 출력 | 내용 |
| --- | --- | --- |
| ① | **회상 후보** | 현재 발화와 선을 문 점들 — 기본 1홉 · 최대 2홉 · weight 상위 N · 총 토큰 상한 |
| ② | **답변 가이드** | `{ mode, allowed, comfortCues, forbidden, followUpQuestions }` |
| ③ | **이야깃거리** | 대화가 끊길 때 던질 화제 — 오래 언급 안 된 쩜 · 다가오는 사건 · 팔로업 거리 |

- 답변 가이드 상세:
  - `mode` 예: 공감 우선 / 편들기 / 축하 / 가볍게 / 안부 — **범용 열거, 호스트가 확장 가능**
  - `comfortCues`: 선에서 찾은 긍정 기록 · 긍정 인물 · 과거의 좋은 시절
  - `forbidden` 기본값: 상대 옹호 · 훈계 · 부정 기억 먼저 꺼내기
  - `followUpQuestions`: 이어묻기 후보 — 빈 필드 · 애매 표현 · 통합 후보
- **Haema는 말을 만들지 않는다.** 가이드는 방향과 재료. 최종 발화는 호스트
- 가이드 구조는 범용. 서비스 특화 지시는 호스트 `hint` 문자열로, Haema는 해석 안 함

**회상 단서(cue)**: 이름·별칭뿐 아니라 **JJ-tag·개념 문자열**도 받는다. 태그 매칭 + 선 확산으로 후보 반환

**valence 정책**:
- 추출 시 AI 어댑터가 valence JJ-tag(긍정/중립/부정) 부여
- Haema가 **"먼저 꺼내는"** 후보(이야깃거리 · 먼저 말 걸 거리)는 **긍정·중립만**
- 부정 점은 회상 후보에 **항상 포함하되 flag로 표시** — 호스트가 "유저가 먼저 꺼냈을 때 알아봐 주는" 용도로만 쓰도록
- 호스트가 "부정이어도 반드시 상기"할 별도 트랙을 원하면 hint로 정의. Haema는 관여 안 함

**고민 쩜 정책 (2026-09-06 확정 · 2-a 구현)**:
- type **"고민"**은 정식 종류. 상태는 meta가 아니라 JJ-tag **"미해결" / "해결"**로. 해결되면 미해결 태그를 떼고
  해결 시점을 사건으로 남긴다 (`resolveConcern`, 콘솔 `resolve`)
- `getProactiveCues`: 부정 valence여도 **type=고민 & 미해결**이면 후보 허용 — 단 결과에 **careful: true** 표시
- 답변 가이드 mode에 **"조심 안부"** 추가 — 내용을 먼저 말하지 말고 "고민 있어?" 수준으로만 열라는 지시
- 상처(부정인 사건·인물 등)는 기존대로 먼저 꺼내지 않는다

**먼저 말 걸 거리 조회 — `getProactiveCues(ownerId, now)`**:
- 회상과 같은 선 탐색. 단서가 "현재 발화"가 아니라 **"현재 시각"**인 것뿐
- 종류: 팔로업(답 비어 있는 쩜) / 다가오는 것(날짜 임박) / 오래된 긍정 쩜 / 패턴(반복 주기 예정 시점)
- 점수 + 이유 함께 반환. 긍정·중립만. **후보 없으면 빈 결과** (억지로 말 걸지 않게)
- 언제 깨울지 · 말 걸어도 되는지 · 푸시 발송은 전부 호스트 몫. Haema는 재료만
- (참고) 첫 호스트는 v1에서 푸시 문구를 고정 풀로 돌리므로 이 함수는 **2단계 후반 우선순위**

**선제 안부 재료 — `getRecentMoodSignals(ownerId)`** (조회 기간 등 인자는 구현 시 확정):
- 최근 점의 valence 분포 · 대화 빈도 변화를 호스트가 조회할 수 있는 함수 하나
- 판단 · 발동 · 쿨다운은 호스트. Haema는 **집계만**

**범위 (구현 항목)**:
- `recall(ownerId, cues, options)` → 위 3종 반환 (후보 스코어링·홉 확산·토큰 상한·valence flag 포함)
- **`AIAdapter` 레퍼런스 구현 3종**(anthropic/openai/google) + 커스텀 함수 주입:
  대화에서 쩜 추출(extract — valence JJ-tag 부여 포함) · summary/관계 요약(summarize) · 회상 후보 점수화(scoreRecallCandidates)
- `getProactiveCues` · `getRecentMoodSignals`
- 사용된 점의 `recallCount` · 선 `lastActivated` 갱신
- 판단 분리: **Haema의 AI 어댑터가 후보를 점수화**까지 한다. 꺼낼지·침묵할지·어떤 말투로 연출할지는 **호스트 챗봇의 몫**
- **도메인 무지 재확인**: 위 모든 것에 특정 서비스 어휘(배변·건강·캐릭터 이름 등) 금지.

**완료 기준:**
- [x] 유닛 테스트: 1홉/2홉 경계, weight 정렬 상위 N 컷, 토큰 상한 잘림, 후보 없음 → 빈 결과(환각 재료 제공 금지) (2-a)
- [x] 매 턴 3종(회상 후보 · 답변 가이드 · 이야깃거리) 반환 구조 테스트 — 이야깃거리·먼저 말 걸 거리에 부정 쩜 미포함, 회상 후보의 부정 점은 flag (2-a, 가이드는 규칙 기반 뼈대)
- [x] cue 확장 테스트 — 이름 없이 JJ-tag 단서만으로 후보 반환 (2-a)
- [x] `getProactiveCues` 후보 없으면 빈 결과 / `getRecentMoodSignals` 집계값만 반환 (2-a)

## 3단계 — 통합 (쩜 통합): 별칭 병합·복원

**범위:**
- `mergeJJums(winnerId, loserId)`: events 병합 + mentionCount 합산 + aliases 추가 +
  `mergedFrom`/`mergedInto` 기록, 패자 `status='merged'` 껍데기화 (putJjums로 원자적 처리)
- `unmergeJJum(...)`: `mergedFrom` 이력 기반 분리 복원 (오병합 롤백)
- `findDuplicateCandidates(ownerId)`: 이름/별칭 겹침 후보 리포트
- 병합 확신도는 **AI 어댑터(judgeMergeCandidate)가 점수화** — 자동 병합할지·되물을지의
  연출은 호스트 챗봇 몫

**완료 기준:**
- [ ] 병합 후 구 이름·별칭 어느 것으로도 단일 쩜 히트
- [ ] 병합→복원 라운드트립 테스트: 원래 두 점으로 원상 복구
- [ ] 병합 중 부분 실패 없음 (putJjums 원자성)

## 5단계 — Firestore 어댑터 + 회원 동기화

**범위:**
- 사용자 본인 쩜·호스트 챗봇 쩜을 함께 생성·저장·연결하는 흐름. 가입 시 호스트가 확정된 서비스는 계정 생성 시, 여러 캐릭터 중 선택하는 서비스는 선택 완료 후 대화창 최초 진입 시 실행한다. AI API 연결과 독립적이며 첫 발화를 기다리지 않는다. 상세 기획은 `해마.ai_최신기획서.md`의 사용자·호스트 자아쩜 최초 생성·연결을 따른다.
- 일반 쩜과 두 자아쩜 모두 언급 횟수 1·회상 횟수 0으로 시작한다. 두 자아쩜은 대화 시작 전 생성 자체를 최초 1회 언급으로 취급하고 생성 시각을 최근 언급 시각으로 기록한다. 로그인·새 세션·재시도에서는 같은 사용자·호스트의 기존 쩜과 횟수를 재사용하며 최초 1회를 다시 부여하지 않는다. 식별 정보와 생성 출처·최초 생성·연결 경로는 `SCHEMA.md`의 v5 생명주기 기획을 바탕으로 구현 전에 확정한다.
- 다른 캐릭터의 대화창에 처음 들어갈 때는 사용자 본인 쩜을 유지하고 해당 호스트 쩜만 추가한다. 선택하지 않은 캐릭터의 쩜은 자동 생성하지 않는다.
- `FirestoreAdapter`: 1단계의 **같은 어댑터 계약 테스트 스위트** 통과 (에뮬레이터 기준)
- `LocalStorageAdapter`(브라우저): 마이풉 게스트=클라이언트 저장 정책용 — 같은 계약 스위트 통과
- 승계 유틸: 게스트(LocalStorage) 쩜 → 회원(Firestore) 업로드 병합 (마이풉 확정 정책:
  게스트=클라이언트 저장 / 회원=동기화)

**완료 기준:**
- [ ] 가입 시 호스트가 확정된 경우 계정 생성 직후 두 자아쩜이 함께 저장·연결되고, 각 쩜의 언급 횟수는 1·회상 횟수는 0·최근 언급 시각은 생성 시각임을 확인
- [ ] 여러 캐릭터를 제공하는 경우 선택 전에는 기본 쩜을 생성하지 않으며, 선택 완료 후 대화창 최초 진입 시 AI 호출·첫 발화 없이 두 쩜이 함께 저장·연결됨을 확인
- [ ] 로그인·새 세션·캐릭터 전환·재진입·재시도·부분 실패 복구에서 기존 쩜의 ID·기억·횟수가 유지되며 중복 생성되지 않음을 확인
- [ ] 각 자아쩜을 사용자가 처음 실제로 언급하면 언급 횟수가 1에서 2로 증가하며, 생성에 따른 초기 1회가 실제 대화 발화나 회상으로 기록되지 않음을 확인
- [ ] 서로 다른 사용자 계정이 격리되고, 현재 사용자·호스트 쩜을 연결한 뒤 발화자와 문맥에 따라 `나·너·I·you`의 지칭 대상을 구분함을 확인
- [ ] 계약 스위트가 LocalStorage/Firestore 양쪽에서 통과 (어댑터 교체 구조 실증)
- [ ] 승계 라운드트립: 게스트 쩜 전부가 회원 계정으로 이전, 중복 없이

## 6단계 — 패키징: @haema/core 공개

**범위:**
- 빌드(ESM + `.d.ts`), README(영/한), 버전 정책(semver, schemaVersion과 분리), 깃헙 공개 → npm 배포
- 마이풉에서 로컬 경로 의존(npm link) 제거 → npm/깃헙 설치로 교체, `memory.ts` 목 완전 삭제
