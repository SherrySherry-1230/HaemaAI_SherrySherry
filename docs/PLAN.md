## AI 어댑터 — 설계 원칙 (2026-09-04 확정)

**Haema는 AI를 직접 호출한다. 단, 역할은 "점을 만드는 것"까지.**

- 하는 일: ① 대화에서 점 추출 ② summary·관계 요약 생성 ③ 병합 후보 판정 ④ 회상 후보 점수화
- 안 하는 일: **유저에게 말하기** (말투·연출·꺼낼지 침묵할지 = 호스트 챗봇 몫) / **기억 지어내기**
- 주입: 개발자가 provider(`"anthropic" | "openai" | "google" | custom`) + model + apiKey 주입.
  **Haema는 키를 저장·로깅하지 않는다** (호출 시 메모리 보관만).
- 레퍼런스 구현 3종 + 커스텀 함수 주입. **작업별 모델 분리 가능** (추출용/판정용 따로 지정).
- 프롬프트는 범용. 서비스 특화 지시는 호스트가 **hint 문자열**로 넘기고, Haema는 hint를
  해석하지 않는다 — 프롬프트에 그대로 전달할 뿐 (도메인 무지 유지).
- 인터페이스: `src/adapters/aiAdapter.ts` (1단계에서 정의, 구현체는 2단계)

## 1단계 — 파일 시스템 어댑터 + 점 저장/조회 (최소 동작 단위)

**범위 (여기까지만):**
- 패키지 골격: `package.json`(`@haema/core`) · `tsconfig`(strict) — **런타임 의존성 0**
  (실행: Node 타입 스트리핑 / 테스트: 내장 `node:test` — vitest 도입은 패키징 단계에서 검토)
- `createCell()` 헬퍼: 기본값 채움 (`schemaVersion=3`, 빈 배열들, 타임스탬프)
- **`FileAdapter`** (`StorageAdapter` 구현체 — 사람이 파인더에서 직접 열어보고 고칠 수 있는 저장소):
  - `local-server/haema/{ownerId}/{canonicalName}.jj` — **점 1개 = .jj 파일 1개** (2칸 들여쓰기)
  - `local-server/haema/_index.jj` — 이름·별칭 → jjumId 조회 인덱스 (유실·불일치 시 파일 스캔으로 자가 복구)
  - 자극(언급·회상·선 갱신) 시 **파일 읽기 → 갱신 → 다시 쓰기** — `mentionCount` ·
    `lastMentioned` · `seons.weight` · `recallCount` 변화가 파일에 실제로 보인다
  - **손으로 고친 파일도 스키마 v3 검증 후 로드** — 깨진 파일은 건너뛰고 리포트, 전체는 계속 동작
  - Firestore 어댑터와 교체 가능 (동일 `StorageAdapter` 계약)
- **테스트 콘솔(CLI)**: 점 생성/조회/자극/선/회상 후보 미리보기 — **AI 호출 없이** 손 조작용
- `AIAdapter` **인터페이스 정의만** 추가 (`src/adapters/aiAdapter.ts` — 구현체는 2단계)
- `local-server/` 는 `.npmignore`(패키지 제외) + `.gitignore`(개인 데이터 미커밋)

**완료 기준 (테스트 가능한 형태):**

**마이풉에서 테스트할 수 있는 것:**
파일 어댑터는 로컬 개발·검증용 — 대표가 **파인더에서 기억 파일을 직접 열어 보고 고칠 수 있다.**
콘솔로 만든 점 .jj를 복사해 피피/푸푸 프롬프트에 수동 주입하면, 회상 발화 톤을
AI 연동 전에 미리 실험할 수 있다. (마이풉 웹 연동용 LocalStorage 어댑터는 5단계)

## 2단계 — 회상 (Recall): 선별 주입 엔진 (설계 확정 2026-09-05 · **2-a 완료 2026-09-06**)

> 두 덩이로 나눠 구현: **2-a 회상 엔진(AI 없이 결정론)** — `src/recall.ts` · `src/proactive.ts` · `src/valence.ts` 완료 /
> **2-b AI 어댑터**(extract·summarize·judgeMerge·score) — 인터페이스 + 레퍼런스 구현(OpenAI SDK 호환
> Upstage Solar Adapter)까지 완료. 단, **대화→추출→저장 통합 파이프라인은 아직 완성되지 않았다.**
> 추출 결과(ExtractedDraft)를 실제 점(JJum)으로 만들어 저장·병합·선 연결까지 묶어 돌리는 주체는
> 아직 코어/호스트에 완전히 조립되지 않았으며, 마이풉 연동도 아직 착수하지 않았다.
> 마이풉↔Haema 연동은 마이풉에 직접 붙이기 전에 임시 웹콘솔(로컬 HTML)로 먼저 돌려보고,
> 그다음 정식 연동하는 순서로 진행한다.

**출력 구조 — 점만 주지 않는다. 매 턴 3종을 반환한다:**

| # | 출력 | 내용 |
| --- | --- | --- |
| ① | **회상 후보** | 현재 발화와 선을 문 점들 — 기본 1홉 · 최대 2홉 · weight 상위 N · 총 토큰 상한 |
| ② | **답변 가이드** | `{ mode, allowed, comfortCues, forbidden, followUpQuestions }` |
| ③ | **이야깃거리** | 대화가 끊길 때 던질 화제 — 오래 언급 안 된 점 · 다가오는 사건 · 팔로업 거리 |

- 답변 가이드 상세:
  - `mode` 예: 공감 우선 / 편들기 / 축하 / 가볍게 / 안부 — **범용 열거, 호스트가 확장 가능**
  - `comfortCues`: 선에서 찾은 긍정 기록 · 긍정 인물 · 과거의 좋은 시절
  - `forbidden` 기본값: 상대 옹호 · 훈계 · 부정 기억 먼저 꺼내기
  - `followUpQuestions`: 이어묻기 후보 — 빈 필드(누구야? 언제?) · 애매 표현 · 통합 후보("박**가 핑크야?")
- **Haema는 말을 만들지 않는다.** 가이드는 방향과 재료. 최종 발화는 호스트
- 가이드 구조는 범용. 서비스 특화 지시는 호스트 `hint` 문자열로, Haema는 해석 안 함

**회상 단서(cue)**: 이름·별칭뿐 아니라 **H-tag·개념 문자열**도 받는다. 태그 매칭 + 선 확산으로 후보 반환
(시나리오 02 — 이름 없이 [즐거움, 스트레스 해소]만으로 핑크 술자리 점이 나와야 한다)

**valence 정책**:
- 추출 시 AI 어댑터가 valence H-tag(긍정/중립/부정) 부여
- Haema가 **"먼저 꺼내는"** 후보(이야깃거리 · 먼저 말 걸 거리)는 **긍정·중립만**
- 부정 점은 회상 후보에 **항상 포함하되 flag로 표시** — 호스트가 "유저가 먼저 꺼냈을 때 알아봐 주는" 용도로만 쓰도록
- 호스트가 "부정이어도 반드시 상기"할 별도 트랙을 원하면 hint로 정의. Haema는 관여 안 함

**고민 점 정책 (2026-09-06 확정 · 2-a 구현)**:
- type **"고민"**은 정식 종류. 상태는 meta가 아니라 H-tag **"미해결" / "해결"**로. 해결되면 미해결 태그를 떼고
  해결 시점을 사건으로 남긴다 (`resolveConcern`, 콘솔 `resolve`)
- `getProactiveCues`: 부정 valence여도 **type=고민 & 미해결**이면 후보 허용 — 단 결과에 **careful: true** 표시
- 답변 가이드 mode에 **"조심 안부"** 추가 — 내용을 먼저 말하지 말고 "고민 있어?" 수준으로만 열라는 지시
- 상처(부정인 사건·인물 등)는 기존대로 먼저 꺼내지 않는다

**먼저 말 걸 거리 조회 — `getProactiveCues(ownerId, now)`**:
- 회상과 같은 선 탐색. 단서가 "현재 발화"가 아니라 **"현재 시각"**인 것뿐
- 종류: 팔로업(답 비어 있는 점) / 다가오는 것(날짜 임박) / 오래된 긍정 점 / 패턴(반복 주기 예정 시점)
- 점수 + 이유 함께 반환. 긍정·중립만. **후보 없으면 빈 결과** (억지로 말 걸지 않게)
- 언제 깨울지 · 말 걸어도 되는지 · 푸시 발송은 전부 호스트 몫. Haema는 재료만
- (참고) 첫 호스트는 v1에서 푸시 문구를 고정 풀로 돌리므로 이 함수는 **2단계 후반 우선순위**

**선제 안부 재료 — `getRecentMoodSignals(ownerId)`** (조회 기간 등 인자는 구현 시 확정):
- 최근 점의 valence 분포 · 대화 빈도 변화를 호스트가 조회할 수 있는 함수 하나
- 판단 · 발동 · 쿨다운은 호스트. Haema는 **집계만**

**범위 (구현 항목)**:
- `recall(ownerId, cues, options)` → 위 3종 반환 (후보 스코어링·홉 확산·토큰 상한·valence flag 포함)
- **`AIAdapter` 레퍼런스 구현 3종**(anthropic/openai/google) + 커스텀 함수 주입:
  대화에서 점 추출(extract — valence H-tag 부여 포함) · summary/관계 요약(summarize) · 회상 후보 점수화(scoreRecallCandidates)
- `getProactiveCues` · `getRecentMoodSignals`
- 사용된 점의 `recallCount` · 선 `lastActivated` 갱신
- 판단 분리: **Haema의 AI 어댑터가 후보를 점수화**까지 한다. 꺼낼지·침묵할지·어떤 말투로 연출할지는 **호스트 챗봇의 몫**
- **도메인 무지 재확인**: 위 모든 것에 특정 서비스 어휘(배변·건강·캐릭터 이름 등) 금지. 예시 데이터는 `SCENARIOS.md`의 범용 예시만

**완료 기준:**
- [x] 유닛 테스트: 1홉/2홉 경계, weight 정렬 상위 N 컷, 토큰 상한 잘림, 후보 없음 → 빈 결과(환각 재료 제공 금지) (2-a)

## 3단계 — 통합 (점 통합): 별칭 병합·복원

**범위:**
- `mergeCells(winnerId, loserId)`: events 병합 + mentionCount 합산 + aliases 추가 +
  `mergedFrom`/`mergedInto` 기록, 패자 `status='merged'` 껍데기화 (putCells로 원자적 처리)
- `unmergeCell(...)`: `mergedFrom` 이력 기반 분리 복원 (오병합 롤백)
- `findDuplicateCandidates(ownerId)`: 이름/별칭 겹침 후보 리포트
- 병합 확신도는 **AI 어댑터(judgeMergeCandidate)가 점수화** — 자동 병합할지·되물을지의
  연출("잠깐, 핑크가 박박**야?!")은 호스트 챗봇 몫

**완료 기준:**
- [ ] 병합 후 구 이름·별칭 어느 것으로도 단일 점 히트
- [ ] 병합→복원 라운드트립 테스트: 원래 두 점으로 원상 복구
- [ ] 병합 중 부분 실패 없음 (putCells 원자성)
- [ ] **`docs/SCENARIOS.md` 시나리오 01의 통합 파트(핑크 ⇄ 박** 병합 · 별칭 승계 · 기존 기억 승계)가 재현되는가** (테스트 정답지)

**마이풉에서 테스트할 수 있는 것:**
"핑크가 박**잖아" → 피피가 자연스럽게 확인 발화("잠깐, 핑크가 박박**야?! 합쳐서 기억할게~")
후 병합되는지. "아니야 딴 사람이야" → 분리 복원되는지. 애매하면 병합하지 않고 되묻는지
(판단 전 질문 원칙 — 되묻기 후보(followUpQuestions)는 Haema가 재료로 제공, 발화·연출은 호스트).

## 4단계 — 정리 (Retention): 자동 정리·감쇠

**범위:**
- 점 상한 정책 — **Haema는 숫자를 모른다**, 호스트가 옵션으로 넘긴다 (호스트 기본 예시: **무료 80 / 프리미엄 500**, 2026-09-06 확정)
- 상한 도달 시 오래된 것부터 `status='archived'` (**삭제 아님**, `pinned` 영구 면제)
- 재언급 시 archived → active 부활
- 선 weight 감쇠 배치(오래 안 쓰인 선 서서히 약화) + `editHistory` 기록(by: 'batch')

**완료 기준:**
- [ ] 상한 시나리오 테스트: 초과 시 정렬 기준대로 archived, 핀 점 면제, 부활 동작
- [ ] archived 점은 list 기본 조회에서 제외되되 데이터는 보존됨을 검증
- [ ] 감쇠 함수 단위 테스트 (시간 경과 시뮬레이션)

**마이풉에서 테스트할 수 있는 것:**
상한 80 시뮬레이션 — 오래된 기억이 잠들고 재언급 시 부활하는지.
**친밀도 = 점 수** 연동: 점이 정리되면 푸푸 말투 레벨이 자연 하락하는지(서먹해짐 연출),
"절대 잊지 마" 핀 점이 정리에서 살아남는지. 상한 안내가 챗이 아닌 웹 관리 화면에만 뜨는지.

## 5단계 — Firestore 어댑터 + 회원 동기화

**범위:**
- `FirestoreAdapter`: 1단계의 **같은 어댑터 계약 테스트 스위트** 통과 (에뮬레이터 기준)
- `LocalStorageAdapter`(브라우저): 마이풉 게스트=클라이언트 저장 정책용 — 같은 계약 스위트 통과
- 승계 유틸: 게스트(LocalStorage) 점 → 회원(Firestore) 업로드 병합 (마이풉 확정 정책:
  게스트=클라이언트 저장 / 회원=동기화)

**완료 기준:**
- [ ] 계약 스위트가 LocalStorage/Firestore 양쪽에서 통과 (어댑터 교체 구조 실증)
- [ ] 승계 라운드트립: 게스트 점 전부가 회원 계정으로 이전, 중복 없이

**마이풉에서 테스트할 수 있는 것:**
게스트로 쌓은 단어집이 **가입 후 그대로 동기화**되는지 ("기기 바꿔도 기록과 단어집이 그대로" =
가입 보상). 기기 A에서 만든 핑크 점을 기기 B의 피피가 기억하는지.

## 6단계 — 패키징: @haema/core 공개

**범위:**
- 빌드(ESM + `.d.ts`), README(영/한), 버전 정책(semver, schemaVersion과 분리), 깃헙 공개 → npm 배포
- 마이풉에서 로컬 경로 의존(npm link) 제거 → npm/깃헙 설치로 교체, `memory.ts` 목 완전 삭제

**완료 기준:**
- [ ] 마이풉이 npm 설치본만으로 1~5단계 기능 전부 회귀 통과
- [ ] 코어 코드에 마이풉 도메인 개념 0건 (grep 검증 — 배변·캐릭터·감정 등 금지어)
