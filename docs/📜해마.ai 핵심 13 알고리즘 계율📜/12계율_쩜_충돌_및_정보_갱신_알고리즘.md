# 12계율 — 쩜 충돌 및 정보 갱신 알고리즘

> 기획 명세이며 구현 완료를 뜻하지 않음.
> 새 발화와 기존 쩜이 달라 보일 때 정정, 시간 변화, 실제 충돌, 동명이인을 구분한다.

## 역할과 읽는 상황

- 기존 쩜에 새 사실을 보태려는데 내용이 어긋날 때 읽는다.
- 별칭이 같은 대상을 가리키는지 의심스러울 때 읽는다.
- 과거 사실을 현재 사실로 회상해도 되는지 판단할 때 읽는다.
- 검색어: 충돌, 정정, 시간 변화, 갱신, 동명이인, 병합, 복원.
- 이 문서는 쩜의 기록을 안전하게 바꾸기 위한 판단 기준이다.
- 실제 업데이트 절차는 3계율, 동일 대상 탐색은 2계율과 연결된다.
- Haema는 meta의 내부 내용을 해석해 충돌을 판정하지 않는다.

## 입력과 확인할 근거

1. 사용자의 최종 발화와 그 시점을 확인한다.
2. 비교 대상 쩜(JJum)의 이름·별칭·기존 사실을 확인한다.
3. 기존 facts의 출처와 기록 시각을 가능한 범위에서 확인한다.
4. events에 별도 사건 시각이 있다면 발화 시각과 구별한다.
5. 사용자가 직접 고친 내용인지 확인한다.
6. 사용자가 '예전에는', '지금은'처럼 시기를 나눴는지 살핀다.
7. 두 정보가 정말 같은 대상과 같은 속성을 가리키는지 확인한다.
8. 동명이인이나 같은 별칭을 가진 다른 대상의 가능성을 살핀다.
9. 쩜선(Seon)의 관계는 보조 근거로만 사용한다.
10. 출처나 시각이 없으면 없는 그대로 보류할 수 있다.
11. 호스트가 제공한 맥락은 명시된 범위에서만 참고한다.
12. 다른 사용자의 쩜은 비교 대상으로 가져오지 않는다.

## 네 가지 경우를 먼저 분리

### 사용자 정정

- 사용자가 '아까 말한 건 틀렸어'처럼 이전 표현을 직접 바로잡는다.
- 정정 대상과 수정 내용을 확인한 뒤 현재 사실을 갱신할 후보로 둔다.
- 정정 이전 표현이 있었다는 기록은 필요한 범위에서 남긴다.
- 모호한 대명사 때문에 대상을 알 수 없으면 확인을 기다린다.

### 시간에 따른 변화

- '예전에는 싫었는데 요즘은 좋아'처럼 시점마다 사실이 다를 수 있다.
- 과거와 현재를 함께 보존할 가치가 있는지 검토한다.
- 앞선 기록이 당시에는 맞았을 수 있으므로 오류로 낙인찍지 않는다.
- 현재 상태를 말할 때는 어떤 시점을 가리키는지 분명히 한다.

### 실제 충돌

- 같은 대상·같은 시점·같은 사실에 서로 양립하기 어려운 내용이 있다.
- 출처, 사용자 확인 여부, 맥락을 비교한다.
- 단순히 나중에 등장했다는 이유만으로 새 내용을 정답으로 삼지 않는다.
- 해결 근거가 부족하면 두 기록의 충돌을 보류한다.

### 동명이인과 별칭 중복

- 같은 이름이나 별칭이 두 사람·장소·사물을 가리킬 수 있다.
- 이름 일치만으로 기존 쩜에 자동 병합하지 않는다.
- '선생님'·'대표님' 같은 호칭만으로 동일 인물이라 확정하지 않는다.
- '아니 그 사람 말고'는 대상 정정이며 저장 사실의 오류 정정과 구별한다.
- 관계, 사건, 사용자의 명시적 동일 대상 확인을 살핀다.
- 확인 전에는 각각의 기억을 섞지 않고 구별한다.

## 판단 순서와 분기

1. 미완성 스냅샷이 아니라 최종 발화인지 먼저 확인한다.
2. 1계율의 개인적 의미를 충족하는 내용인지 살핀다.
3. 2계율에 따라 같은 대상인지 후보를 찾는다.
4. 동일 대상인지 확신할 수 없으면 동명이인 가능성을 먼저 검토한다.
5. 사용자가 명시적으로 정정했는지 확인한다.
6. 정정이 아니면 시기 차이로 두 사실이 공존 가능한지 확인한다.
7. 둘 다 아니면 같은 시점의 실제 충돌인지 확인한다.
8. 각각의 사실에 근거와 시점을 연결해 둔다.
9. 명확한 정정은 현재 표현을 바꿀 후보로 3계율에 넘긴다.
10. 시간 변화는 이전 사실을 지우지 않는 갱신 후보로 넘긴다.
11. 미해결 충돌은 사실을 하나로 합쳐 저장하지 않는다.
12. 호스트 회상에는 불확실한 사실을 단정하지 않도록 알린다.
13. 사람이 직접 수정한 .jj 파일도 v4 검증을 거쳐야 한다.
14. 원문이나 고유 표현의 의미를 멋대로 정규화하지 않는다.

## 병합과 복원의 경계

- 사용자가 핑크와 박**가 같은 사람이라고 확인하면 통합 후보가 된다.
- 같은 이름만 보고 병합하지 않는다.
- 병합 이력의 취지는 이전 쩜을 추적하고 오병합을 복원할 수 있게 하는 것이다.
- v4에는 mergedFrom, mergedInto, editHistory가 있다.
- 이 필드들의 존재가 안전한 자동 병합·복원 구현을 보장하지는 않는다.
- 어떤 내용을 유지하고 어떤 쩜선을 옮길지 설계가 필요하다.
- 잘못 합쳐진 기억을 어떻게 분리·복구할지도 설계가 필요하다.
- 복원 절차가 정해지기 전에는 애매한 대상을 성급히 합치지 않는다.

## 출력과 다음 문서

출력은 설명용 판단 기록이며 신규 API나 저장 필드를 제안하지 않는다.

- 비교한 기존 사실과 새 발화를 적는다.
- 경우를 정정·시간 변화·충돌·동명이인 후보로 분류한다.
- 판단 근거가 되는 사용자 표현과 시점을 적는다.
- 확정 가능한 내용과 확인이 필요한 내용을 분리한다.
- 갱신 또는 병합을 보류한 이유를 적는다.
- 동일 대상 판단은 [2계율](./2계율_기존_쩜_탐색_알고리즘.md)과 잇는다.
- 실제 내용 갱신은 [3계율](./3계율_기존_쩜_업데이트_알고리즘.md)에 넘긴다.
- 회상 중 불확실성은 [6계율](./6계율_회상_알고리즘.md)에 전달한다.

## 실패와 보류

- 기존 쩜을 읽지 못하면 새 사실을 기존 사실 위에 덮어쓰지 않는다.
- 출처가 불명확하면 최신 시각만으로 진위를 가리지 않는다.
- 대상이 모호하면 같은 이름을 가진 쩜을 자동 통합하지 않는다.
- 병합 기록이 불완전하면 복원 가능하다고 단정하지 않는다.
- 사용자 정정 범위가 불명확하면 필요한 부분을 확인 대상으로 남긴다.
- 충돌 해결 전 호스트가 사실처럼 말하지 않도록 불확실성을 표시한다.

## 가상 예시

### 1. 사용자의 직접 정정

- 이전 발화: '카페는 성수동에 있어.'
- 새 발화: '아까 잘못 말했어. 건대 쪽이야.'
- 판단: 같은 카페를 가리키는지 확인한 뒤 위치 정정 후보로 둔다.
- 출력: 과거 기록을 조용히 지우지 않고 정정 근거를 남긴다.

### 2. 취향의 시간 변화

- 과거: '민초는 싫어.'
- 현재: '요즘은 민초도 가끔 먹어.'
- 판단: 과거 표현이 틀렸다기보다 취향이 변했을 수 있다.
- 출력: 시기를 구별한 갱신 후보를 만든다.

### 3. 실제로 양립하기 어려운 정보

- 기존 기록: '면접은 화요일이었다.'
- 새 발화: '그 면접은 목요일이었어.'
- 판단: 같은 면접인지와 어느 날짜에 근거가 있는지 확인한다.
- 출력: 확인 전에는 화요일·목요일 중 하나를 단정하지 않는다.

### 4. 같은 별칭의 다른 사람

- 기존 쩜: 고교 친구 '핑크'.
- 새 발화: '회사에도 핑크라는 분이 있어.'
- 판단: 별칭은 같지만 다른 사람일 수 있다.
- 출력: 고교 친구의 술자리 기억을 회사 사람에게 옮기지 않는다.

### 5. 호칭과 대상 정정

- 발화: '대표님이랑 갔어. 아니, 그 사람 말고 예전 대표님.'
- 판단: '대표님' 호칭을 공유해도 인물은 둘일 수 있다.
- 출력: 대상을 다시 탐색하고, 기존 인물의 사실을 덮어쓰지 않는다.

## 검수 기준

- 네 경우가 문서와 판단 기록에서 분리된다.
- 명시적 사용자 정정을 보존하면서 현재 사실을 다룬다.
- 시간 변화의 과거 사실을 무조건 오류로 처리하지 않는다.
- 최신 발화가 언제나 이긴다는 규칙이 없다.
- 이름만 같은 대상을 병합하지 않는다.
- 호칭과 '아니 그 사람 말고'를 동일성 판단과 사실 정정에서 구분한다.
- 병합·복원은 설계 필요로 남고 구현 완료로 표현되지 않는다.
- meta를 읽거나 Haema가 사용자에게 직접 확인 질문을 보내지 않는다.

- 정정·충돌의 확정 기준과 사용자 확인 절차는 미확정이다.
- 병합 시 데이터 이동, 오병합 분리, 복원 절차도 별도 설계가 필요하다.
