# 3계율 · 기존 쩜 업데이트 알고리즘

> 해마.ai 핵심 13 알고리즘 계율 · 기획 명세, 구현 완료를 뜻하지 않음.
> 목적: 확인된 기존 JJum에 새 근거를 보태되 과거 사실·출처·사용자 정정을 잃지 않는다.
> 아래 판단 기록은 설명용이며 구현된 API, 새 저장 필드 또는 확정된 점수 체계가 아니다.

## 역할과 경계

[2계율](./2계율_기존_쩜_탐색_알고리즘.md)이 같은 대상을 가리키는 기존 쩜을 확인한 뒤 이 문서를 읽는다.
사용자의 새 진술을 사실·사건·별칭·쩜태그(JJ-tag)·요약·언급 기록에 어떻게 반영할지 가른다.
기존 쩜의 jjumId와 ownerId는 업데이트 과정에서 유지한다.
서로 다른 두 쩜을 합치는 작업은 이 문서의 단순 갱신이 아니라 [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md)의 통합 검토다.
과거 기억을 지우는 대신, 현재 사실과 과거 사실의 시점을 구별한다.
Haema는 meta의 서비스별 내용을 해석하지 않고 그대로 보존한다.
호스트에게 전달할 답변 방향과 기억 재료는 [7계율](./7계율_답변_가이드_생성_알고리즘.md)에서 다룬다. 최종 답변 문장과 말투는 호스트가 만든다.

### 이 문서를 읽는 상황 · 검색어

- 예전에 저장한 인물·장소·취향에 새 사실이 붙을 때: “기존 쩜 갱신”, “새 사실”.
- 사용자가 자신이 한 말을 바로잡을 때: “정정”, “오탈자”, “출처”.
- 시간이 지나 상태가 바뀌었을 때: “변화”, “이전”, “현재”, “사건”.
- 별칭이나 대표 이름이 추가·수정될 때: “별칭”, “jjumName”.
- 두 진술이 맞부딪힐 때: “모순”, “충돌”, “보류”.
- 여러 쩜이 함께 언급될 때: “쩜선”, “관계 label”.
- 입력 중 스냅샷과 전송한 최종 문장이 다를 때: “잠정”, “최종 발화”.

## 필요한 입력

1. ownerId와 [2계율](./2계율_기존_쩜_탐색_알고리즘.md)이 확인한 기존 쩜의 jjumId.
2. 기존 쩜의 facts, events, summary, aliases, jjtags, context, seons와 통계·관리 이력.
3. 새 발화의 원문, 시점, 사용자가 말한 대상과 새 사실의 근거.
4. 잠정 스냅샷인지, 사용자가 보낸 최종 발화인지에 대한 구분.
5. 정정·부인·동일 대상 선언처럼 사용자가 명시적으로 밝힌 관계.
6. 실제로 연결할 다른 쩜이 있다면 그 쩜의 확인된 jjumId.

저장 필드는 [v4 스키마](../SCHEMA.md)의 이름과 의미만 사용한다.
파일명은 쩜 내부의 jjumName과 구분한다. 파일명을 보고 새로운 사실을 추론하지 않는다.
같은 이름이라고 다른 사람의 사실을 가져오지 않는다.
서비스별 hint가 있더라도 meta 내용에서 의미를 읽어 업데이트 규칙을 만들지 않는다.

## 판단 단계

### 1. 대상과 근거를 재확인한다

기존 쩜 하나가 맞는지 [2계율](./2계율_기존_쩜_탐색_알고리즘.md)의 근거를 다시 확인한다.
새 발화가 다른 동명이인이나 다른 사건을 말한다면 갱신을 멈춘다.
출처가 대화인지 사용자 직접 편집인지, 과거에 기록된 사실인지 구별한다.
명시되지 않은 속성·관계·시점을 그럴듯하다는 이유로 추가하지 않는다.
미완성 스냅샷에 대해서는 잠정 변경 후보만 기록한다.
최종 발화가 도착하면 잠정 내용을 다시 읽고 갱신 판단을 확정한다.
잠정 후보의 세부 영구 저장 시점은 아직 확정되지 않았다.

### 2. 새로움과 반복을 구별한다

같은 사실을 다시 말했으면 쩜을 하나 더 만들지 않는다.
반복 언급은 mentionCount와 lastMentioned에 반영할 수 있다.
서로 다른 사실이면 기존 facts에 근거와 시점을 갖춘 새 조각으로 더한다.
사건이라면 events에서 언제 무엇이 있었고 어떤 쩜이 함께 나왔는지 구분한다.
refJJumIds에는 실제로 확인한 쩜의 ID만 넣는다.
같은 사건을 이름만 바꾸어 중복 기록하지 않도록 앞선 기록과 대조한다.
어느 정도 표현 차이를 같은 사실로 볼지는 아직 정량 기준이 없다.

### 3. 정정과 시간 변화를 나눈다

“내가 아까 잘못 말했어”는 사용자가 밝힌 정정 근거다.
“이제 그 일을 그만뒀어”는 과거 사실이 틀렸다는 뜻이 아니라 상태 변화일 수 있다.
과거 진술을 현재 사실로 덮지 않고 facts·events·editHistory에 변화의 맥락을 남긴다.
한 진술을 폐기해야 하는지 판단이 불명확하면 [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md)로 넘긴다.
사용자의 오탈자는 의미가 분명할 때 교정하되 원문 뜻을 바꾸지 않는다.
신조어·개인적 표현의 뜻이 불분명하면 사용자 확인 없이 표준어로 바꾸지 않는다.
“어제”·“지난주”의 사건 날짜는 입력 시각과 전달된 시간대가 충분할 때만 확정한다.
시간대가 없거나 발화 기준 시점이 불명확하면 절대 날짜를 지어내지 않고 확인을 기다린다.
한국 우선 타깃이어도 모든 사용자의 시간대를 한국으로 고정하지 않는다.

### 4. 이름·쩜태그·요약을 보강한다

새 별칭은 같은 대상이라는 근거가 있을 때만 aliases에 더한다.
“언니”·“선배”·“우리 엄마” 같은 호칭은 관계 단서이지 그 자체로 유일한 별칭은 아니다.
띄어쓰기·오탈자 교정은 원문 의미가 분명할 때만 적용하고, 사용자의 한글 표현을 로마자로 강제 변환하지 않는다.
대표 이름 변경은 기존 jjumId를 유지하면서 내부 jjumName을 고치는 일이다.
대표 이름이 바뀌면 보호 규칙을 적용한 파일명도 점검하되, 파일명은 ID가 아니다.
jjtags는 대상의 분류와 정서가를 담는다. 추정만으로 낙인을 찍지 않는다.
기존의 유효한 쩜태그를 새 표현 한 번 때문에 무조건 제거하지 않는다.
summary는 축적된 사실과 변화를 읽기 쉽게 압축하되 없는 관계를 만들어 쓰지 않는다.
요약이 실패하면 확인된 사실·사건은 보존하고 요약 변경만 보류한다.
“친한 사람”처럼 쩜선과 기록에서 얻은 해석은 사용자의 직접 발언과 구별한다.

### 5. 쩜선을 손본다

함께 등장한 두 쩜의 대상이 확인되면 seons의 targetId에 실제 jjumId를 사용한다.
같은 상대·같은 label의 쩜선은 중복을 만들지 않고 기존 쩜선의 연결 강도 갱신을 검토한다.
같은 상대라도 label이 다르면 별도 쩜선을 유지할 수 있다.
관련 이름만 있고 ID를 찾지 못했으면 targetId에 이름을 대입하지 않는다.
사용되지 않은 쩜선의 감쇠는 쩜 자체의 삭제가 아니다.
쩜선 weight의 수치 계산·갱신 폭은 이 문서에서 새로 정하지 않는다.
회상에서 어떤 쩜선을 따라갈지는 [6계율](./6계율_회상_알고리즘.md)에 넘긴다.

### 6. 소속과 이력을 지킨다

ownerId, sourceService, meta, mergedFrom, responseFeedback를 이유 없이 비우지 않는다.
수정 사실은 editHistory의 date, action, field, by 의미에 맞춰 남긴다.
상태 status나 pinned를 사용자 뜻과 무관하게 바꾸지 않는다.
회상 횟수 recallCount와 마지막 회상 시각 lastRecalled는 언급 기록과 구별한다.
신뢰도나 중요도를 별도 필수 필드로 만들어 넣지 않는다.
그 기준과 저장 방식은 현재 v4 스키마에서 미확정이다.

## 분기 · 출력 · 넘길 문서

| 상황 | 판단 기록 | 처리 방향 |
| --- | --- | --- |
| 확인된 기존 쩜의 새 사실 | 새 fact 또는 event 후보 | 기존 쩜 갱신 |
| 같은 사실의 반복 언급 | 새 쩜·중복 fact 없음 | 언급 기록 검토 |
| 사용자 명시 정정 | 바뀐 부분과 과거 근거 보존 | 충돌 확인 후 갱신 |
| 시점이 달라진 상태 | 이전·현재를 구별 | 사건과 요약 갱신 검토 |
| 대상 자체가 모호함 | 기존 쩜은 그대로 | [2계율](./2계율_기존_쩜_탐색_알고리즘.md)로 되돌림 |
| 서로 다른 저장 쩜의 통합 문제 | 단순 갱신으로 처리하지 않음 | [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md) |
| 관련 이름의 ID가 불명확함 | 쩜선 추가 보류 | 확인 근거 요청 |
| 민감정보가 포함됨 | 보호 판단 필요 | [13계율](./13계율_개인정보_및_민감정보_처리_알고리즘.md) |

출력은 어느 기존 쩜에 무엇을 왜 바꿀지 설명하는 해마 판단 기록이다.
예시: “jjumId가 확인된 카페 쩜 / 사실 추가 / 사용자의 오늘 진술 / 날짜 확인 필요”.
이 기록은 구현된 메서드 반환형이나 새 스키마 필드가 아니다.
확정된 갱신 결과만 저장 단계로 넘기고, 보류된 부분은 덮어쓰지 않는다.
가이드는 [7계율](./7계율_답변_가이드_생성_알고리즘.md), 회상 후보는 [6계율](./6계율_회상_알고리즘.md)이 별도로 판단한다.

## 보류 · 실패 처리

- 저장소 읽기에 실패하면 빈 쩜을 만들어 대체하지 않는다.
- 기존 파일 하나가 손상되면 손상 사실을 드러내고 임의 복원으로 갱신하지 않는다.
- 저장 쓰기에 실패하면 갱신 완료로 보고하지 않는다.
- 사용자 진술이 서로 모순되면 어느 한쪽을 사실로 지어내지 않는다.
- 쩜태그, 별칭, 요약 생성이 실패해도 확인된 기존 기억을 삭제하지 않는다.
- 입력 중 스냅샷이 뒤집히면 잠정 판단을 취소하고 최종 발화 기준으로 다시 본다.
- 다른 ownerId의 같은 이름 쩜으로 대신 저장하지 않는다.
- 보조 모델의 판단이 실패하면 사용자 근거와 기존 기록에 기반한 판단으로 돌아간다.

## 가상 상황

### 예시 1 · 새 경험 추가

사용자: “핑크랑 어제도 술을 마셨어.”
저장 쩜: 핑크가 오래된 친구라는 사실과 지난 만남 기록.
판단: 같은 대상이 확인되면 새 만남의 사건 후보를 보태고 언급 기록을 갱신한다.
주의: “어제”의 날짜는 입력 시각·전달된 시간대가 충분할 때만 확정한다.
주의: 지난 만남의 날짜와 이번 만남을 한 사건으로 합치지 않는다.

### 예시 2 · 사용자의 정정

사용자: “아까 토요일이라고 했는데 일요일이야.”
저장 쩜: 이번 약속 날짜가 토요일이라고 잠정 기록됨.
판단: 최종 발화의 정정 근거를 우선하며 편집 이력에 수정 사실을 남긴다.
주의: 정정 전 기록을 조용히 지워 근거를 잃지 않는다.

### 예시 3 · 시간이 흐른 사실

사용자: “작년에는 그 회사에 다녔고 지금은 다른 곳에서 일해.”
저장 쩜: 작년 회사와의 관계.
판단: 과거 재직과 현재 변화를 시점이 다른 정보로 기록한다.
주의: 이전 재직 자체를 거짓으로 고치지 않는다.

### 예시 4 · 동명이인 중지

사용자: “우리 팀에도 핑크가 있는데 옛 친구 핑크와는 다른 사람이야.”
저장 쩜: 옛 친구 핑크.
판단: 기존 쩜을 갱신하지 않고 [2계율](./2계율_기존_쩜_탐색_알고리즘.md)·[4계율](./4계율_신규_쩜_생성_알고리즘.md)을 다시 검토한다.
주의: 같은 이름을 이유로 과거 사실을 새 사람에게 옮기지 않는다.

### 예시 5 · 여러 관계의 쩜선

사용자: “같은 친구가 내 작업을 도와줬고 여행도 같이 갔어.”
저장 쩜: 친구와 작업·여행 쩜의 정체가 각각 확인됨.
판단: 관계 의미가 다르면 서로 다른 label의 쩜선을 검토한다.
주의: 실제 jjumId가 확인되지 않은 이름은 쩜선의 targetId로 쓰지 않는다.

## 검수 기준

- 확인된 같은 jjumId에서만 갱신하며 ownerId가 바뀌지 않는다.
- 새 사실과 반복 언급, 정정과 시간 변화를 서로 다르게 처리한다.
- facts·events의 출처와 과거 맥락, editHistory를 잃지 않는다.
- summary나 jjtags가 사실을 넘어서는 단정으로 바뀌지 않는다.
- 다른 label의 쩜선을 한 줄로 압축하지 않고 이름을 ID로 저장하지 않는다.
- meta를 읽어 분기하지 않고 불필요하게 덮지 않는다.
- 스냅샷 잠정 변경과 최종 발화의 확정 변경을 구분한다.
- 실패와 모순은 갱신 완료로 포장하지 않는다.

## 기획 근거와 미확정 항목
