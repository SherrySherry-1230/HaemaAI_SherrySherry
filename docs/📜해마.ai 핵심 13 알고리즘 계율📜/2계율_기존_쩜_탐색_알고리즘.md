# 2계율 · 기존 쩜 탐색 알고리즘

> 해마.ai 핵심 13 알고리즘 계율 · 기획 명세, 구현 완료를 뜻하지 않음.
> 목적: [1계율](./1계율_쩜_추출_알고리즘.md)이 찾은 기억 후보가 이미 저장된 누구의 어떤 쩜과 관계있는지 살핀다.
> 이 문서의 판단 기록 예시는 설명용이다. 구현된 API나 저장 타입을 선언하지 않는다.

## 역할과 경계

기존 쩜 탐색은 새 정보를 곧바로 새 쩜으로 만들거나 기존 쩜에 덮어쓰지 않기 위한 확인 단계다.
대표 이름, 별칭, 쩜태그(JJ-tag), 사실, 사건과 대화 맥락을 함께 본다.
이름이 같다는 사실은 검색 단서다. 동일인 또는 동일 대상이라는 결론은 아니다.
의미가 비슷하다는 사실도 비교 단서다. 의미 유사도만으로 병합하지 않는다.
확인된 기존 쩜 하나를 갱신할지, 새 쩜이 필요한지, 판단을 보류할지를 가른다.
서로 다른 두 기존 쩜의 통합과 충돌 처리는 [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md)의 범위다.
Haema는 서비스별 meta 값을 읽어 동일성이나 종류를 판정하지 않는다.

### 이 문서를 읽는 상황 · 검색어

- 1계율이 개인적 의미가 있는 쩜 후보를 내놓은 직후: “기존 쩜”, “같은 대상”.
- 사용자가 새 이름·별칭·호칭을 사용했을 때: “별칭”, “대표 이름”, “정체 확인”.
- 같은 이름의 쩜이 둘 이상 보일 때: “동명이인”, “이름 충돌”.
- 기억과 반대되는 새 진술이 들어왔을 때: “모순”, “정정”, “시간 변화”.
- 입력 중 스냅샷에서 후보가 오르내릴 때: “잠정 후보”, “최종 발화”.
- 파일명만 마스킹되어 보일 때: “파일명”, “내부 jjumName”.

## 필요한 입력

1. 현재 기억 주인의 ownerId와 해당 주인의 저장된 쩜 목록.
2. 사용자의 현재 발화 또는 입력 중 스냅샷, 앞뒤 대화와 입력 시점.
3. [1계율](./1계율_쩜_추출_알고리즘.md)이 뽑은 개인적 의미 후보와 그 근거 표현.
4. 각 저장 쩜의 jjumId, jjumName, aliases, type, jjtags, facts, events, context, seons.
5. 사용자 본인이 과거에 명시한 동일·상이 관계나 정정의 기록이 있다면 그 근거.

jjumId는 저장된 쩜을 가리키는 고유 ID이고, 이름·별칭·파일명은 ID가 아니다.
마스킹된 .jj 파일명은 표시용 보호 결과일 뿐, 내부 jjumName과 비교 대상이 다르다.
조회는 ownerId 범위를 벗어나지 않는다.
meta는 전달·보존할 수 있지만 내용을 해석하지 않는다.

## 판단 순서

### 1. 후보의 성격을 먼저 확인한다

개인적 의미가 부족한 일반 단어라면 1계율로 돌려보내고 쩜을 찾기 위해 의미를 꾸며내지 않는다.
사용자가 실제로 말한 대상·관계·시점을 후보 근거로 묶어 둔다.
스냅샷의 미완성 문구는 잠정 후보라고 표시한다.
사용자가 최종 발화를 확정하면 바뀐 문구를 기준으로 다시 판단한다.
잠정 후보를 어느 시점에 영구 저장할지는 아직 확정되지 않았다.

### 2. 같은 주인의 직접 단서를 찾는다

대표 이름의 일치와 별칭의 일치를 각각 확인한다.
띄어쓰기·표기 차이는 검색 실마리로 삼되, 그것만으로 동일성을 확정하지 않는다.
쩜태그는 범주 단서다. 같은 jjtags를 가진 여러 쩜을 하나로 취급하지 않는다.
파일명에 가린 글자를 임의로 복원하여 이름을 추측하지 않는다.
검색 결과가 없더라도 바로 신규 확정으로 뛰지 않고 내용·맥락을 살핀다.

#### 한국어 표현을 읽을 때

“핑크랑”·“핑크에게”는 “핑크”에 조사가 붙은 발화일 수 있다. 전체 문자열을 곧바로 새 이름으로 등록하지 않는다.
반대로 모든 단어의 끝 글자를 기계적으로 떼지 않는다. 원문과 문장 안의 역할을 함께 확인한다.
“언니”·“선배”·“우리 엄마” 같은 호칭만으로 서로 다른 사람을 하나로 합치지 않는다.
띄어쓰기 차이와 분명한 오탈자는 검색 후보를 넓히는 실마리이며 자동 별칭 확정 근거는 아니다.
“그 카페”처럼 지시어가 앞선 문맥을 가리킬 수 있어도 대상이 여럿이면 확인 전까지 보류한다.
한국어를 우선 살피되 사용자마다 다른 말투·표현을 같은 뜻으로 강제하지 않는다.

### 3. 내용과 대화 맥락을 비교한다

후보가 가리키는 사람·장소·사건·물건 등의 대상과 저장 쩜의 범위를 맞춘다.
facts와 events에서 같은 사건, 관계, 시기, 함께 등장한 대상을 찾는다.
서로 다른 시점의 사실은 변화일 수 있고, 같은 시점의 상반된 사실은 충돌일 수 있다.
context는 형성 맥락을 확인하는 데 쓰되 서비스 확장 meta의 내용은 판단 근거로 읽지 않는다.
쩜선은 관련 기억을 찾는 실마리다. 연결되어 있다는 이유만으로 두 쩜을 하나로 만들지 않는다.
기록되지 않은 관계를 추정하여 새 별칭이나 쩜선을 확정하지 않는다.

### 4. 명시적 근거와 불확실성을 분리한다

사용자가 “박**가 핑크야”라고 밝히면 동일 대상 판단의 직접 근거가 된다.
사용자가 “회사 동료 핑크와 옛 친구 핑크는 다른 사람”이라고 밝히면 별도 대상으로 유지한다.
같은 이름, 함께 등장, 비슷한 설명만 있는 경우에는 후보 관계로 남긴다.
서로 다른 기존 쩜을 합치는 결정은 이 단계에서 실행하지 않는다.
충돌하는 내용은 어느 쪽이 맞는지 지어내지 않고 [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md)로 넘긴다.

“갱신 대상”은 대화에서 같은 쩜에 사실을 더할지 판단한 결과다.
“통합 검토 대상”은 서로 다른 쩜 둘을 합칠지 검토하는 일이며 같은 뜻이 아니다.
확인 질문의 실제 문장과 발화 시점은 호스트가 결정한다.

## 출력 · 넘길 문서

이 단계는 저장된 JJum을 변경하지 않고 판단 기록을 전달한다.
기록에는 현재 후보의 표현, 비교한 기존 jjumId, 일치·상이 근거, 불확실한 부분을 적는다.
추가로 갱신 대상·신규 대상·통합 검토·보류·기억 제외 중 어느 분기인지 밝힌다.
다음 계율에는 확정된 근거만 전달하고, 잠정 후보는 잠정이라고 표시한다.
관련 이름이 실제 jjumId로 확인되지 않았다면 쩜선 targetId를 만들어 넣지 않는다.
기존 쩜을 갱신할 때는 [3계율](./3계율_기존_쩜_업데이트_알고리즘.md), 신규 생성은 [4계율](./4계율_신규_쩜_생성_알고리즘.md)로 넘긴다.
회상 가능성만 확인하려는 경우에는 [6계율](./6계율_회상_알고리즘.md)을 읽는다.
보호가 필요한 정보는 [13계율](./13계율_개인정보_및_민감정보_처리_알고리즘.md) 판단을 먼저 받는다.

### 판단 기록 예시

> 후보 표현: “핑크” / 후보 종류: 인물
> 저장 쩜: jjumId가 있는 “핑크” 한 건
> 근거: 사용자가 옛 친구라고 설명함
> 분기: 기존 쩜 갱신 대상
> 보류: 본명은 아직 확인되지 않음

위 형식은 해마의 판단을 사람이 읽기 쉽게 설명한 예시이며 새 필수 저장 필드가 아니다.

## 보류와 실패 처리

- 저장소를 읽을 수 없으면 “기존 쩜 없음”으로 단정하지 않는다. 탐색 실패를 별도로 남긴다.
- 손상된 쩜 하나는 다른 쩜 탐색을 멈추게 하지 않되, 그 쩜과의 동일성은 확정하지 않는다.
- ownerId를 확인하지 못하면 다른 주인의 기록에서 대신 찾지 않는다.
- 한 이름에 여러 후보가 있으면 임의로 첫 번째를 선택하지 않는다.
- 새 발화가 앞선 스냅샷을 뒤집으면 잠정 판단을 다시 연다.
- Laya 같은 보조 판단이 실패하거나 불확실해도 보조 점수만으로 확정하지 않는다.
- 확인 질문에 답이 없으면 기존 내용도, 새 내용도 억지로 병합하지 않는다.

## 가상 상황

### 예시 1 · 별칭이 확인된 친구

사용자: “핑크랑 어제 만났어.”
저장 쩜: “박**”의 aliases에 “핑크”가 있고, 사용자 진술에도 같은 친구라는 근거가 있다.
판단 근거: “핑크랑”을 통째로 신규 이름으로 삼지 않고 문장 속 “핑크”와 조사를 구별한다.
판단: 같은 쩜의 새 사건·언급 후보로 [3계율](./3계율_기존_쩜_업데이트_알고리즘.md)에 넘긴다.
주의: 별칭 일치만 있고 대상 근거가 모순되면 보류한다.

### 예시 2 · 같은 이름의 다른 사람

사용자: “새 팀에도 민지가 있어. 옛 동아리 민지랑 다른 사람이야.”
저장 쩜: 동아리 민지 한 건.
판단: 명시적 상이 근거가 있으므로 기존 쩜에 덮어쓰지 않고 [4계율](./4계율_신규_쩜_생성_알고리즘.md)의 신규 후보로 넘긴다.
주의: 두 사람의 jjumName이 같을 수 있어도 jjumId는 각각 따로 둔다.

### 예시 3 · 맥락만 비슷한 카페

사용자: “비 오는 날 그 카페에 또 갔어.”
저장 쩜: 비 오는 날과 연결된 카페가 두 곳.
판단: 관련 후보 둘을 보여 주되 장소를 하나로 단정하지 않는다.
다음: 호스트에게 어느 카페인지 확인할 질문 재료를 준다.

### 예시 4 · 새 개인 경험

사용자: “이사 온 뒤 매주 토요일 강변을 걷게 됐어.”
저장 쩜: 해당 습관이나 장소를 가리키는 기록이 없음.
판단: 개인적 의미가 있으므로 [4계율](./4계율_신규_쩜_생성_알고리즘.md)로 넘긴다.
주의: “토요일”이라는 일반 시간 표현만 따로 새 쩜으로 만들지는 않는다.

### 예시 5 · 바뀐 사실인지 충돌인지

사용자: “이제 그 팀에서 일 안 해.”
저장 쩜: “그 팀에서 일함”이라는 과거 사실.
판단: 같은 사람의 이력일 수 있으나 퇴사 시점과 지칭 대상 확인이 필요하다.
다음: [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md)에서 시간 변화·정정·모순을 가르고 [3계율](./3계율_기존_쩜_업데이트_알고리즘.md)로 넘긴다.

## 검수 기준

- 다른 ownerId의 쩜이 비교 결과나 판단 기록에 섞이지 않는다.
- 이름·별칭·쩜태그의 단서와 동일 대상의 확정 근거가 구별된다.
- 같은 이름의 다른 사람, 유사한 사건, 마스킹 파일명을 자동 병합하지 않는다.
- 기존 쩜 갱신과 두 쩜 통합이 다른 분기로 기록된다.
- 불명확한 관련 이름을 jjumId로 꾸미지 않는다.
- 스냅샷 후보와 최종 발화 판단이 구별된다.
- 읽기 실패는 “없는 기억”으로 바뀌지 않고 보류·오류로 전달된다.
- 판단 기록을 스키마 필드나 구현 완료된 API로 오인하지 않게 표시한다.

- [사용 시나리오](../USAGE_SCENARIOS.md)의 “핑크 ⇄ 박**”는 사용자 확인을 거친 통합 예다.
- [v4 스키마](../SCHEMA.md)는 jjumId와 이름·별칭, jjtags, 사실·사건·쩜선을 구분한다.
- [1계율](./1계율_쩜_추출_알고리즘.md)의 추출 근거를 잃지 않고 [3계율](./3계율_기존_쩜_업데이트_알고리즘.md)·[4계율](./4계율_신규_쩜_생성_알고리즘.md)로 분기한다.
- 미확정: 의미 유사성의 계산법·판정 기준·임계값.
- 미확정: 동명이인 확인 질문을 언제 호스트에게 노출할지.
- 미확정: 입력 중 잠정 후보를 영구 저장하는 정확한 시점.
- 미확정: 손상된 파일 복구와 불확실한 기존 쩜의 최종 처리 책임.
