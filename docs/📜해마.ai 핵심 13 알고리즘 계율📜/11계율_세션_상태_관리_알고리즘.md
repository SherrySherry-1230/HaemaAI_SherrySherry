# 11계율 — 세션 상태 관리 알고리즘

> 기획 명세이며 구현 완료를 뜻하지 않음.
> 입력 흐름에 맞춰 해마.ai의 작업 상태를 바꾸고 재개·종료 시 놓친 기억을 점검한다.

## 역할과 읽는 상황

- 호스트 환경을 확인하고 새 대화를 시작할 때 읽는다.
- 사용자가 타이핑을 시작·중단·재개·확정할 때 읽는다.
- 호스트 답변 뒤 다음 발화를 기다리거나 세션을 종료할 때 읽는다.
- 검색어: 세션, 스냅샷, 0.5초, 대기 3초, 비활성 5초, 재개, 종료.
- Haema의 내부 작업 상태를 다루며 호스트 AI의 채팅 표시를 지시하지 않는다.
- 서비스별 세션 정보는 호스트가 제공한 범위에서만 참조한다.
- meta의 내용을 해석해 상태를 바꾸지 않는다.

## 상태의 뜻

- **활성:** 대화에 필요한 컨텍스트가 준비되어 새 입력을 받을 수 있다.
- **입력 중:** 사용자의 수정 중인 발화를 스냅샷으로 보고 있다.
- **대기:** 입력 중단이 3초 이상이어서 재입력을 기다린다.
- **비활성:** 입력 중단이 5초 이상이어서 현재 작업을 쉬는 상태다.
- **종료:** 명시적인 세션 종료 절차를 마친 상태다.
- 비활성은 영구 종료나 쩜 삭제를 뜻하지 않는다.
- 사용자가 다시 입력하면 기존 대화 맥락을 확인한 뒤 재개할 수 있다.
- 상태는 쩜의 active·resting·merged와 다른 개념이다.

## 입력과 확인 사항

1. 사용자와 세션을 구별하는 호스트의 기본 정보를 받는다.
2. 현재 호스트와 서비스 환경을 확인한다.
3. 접근 가능한 쩜통과 필요한 관계 정보를 확인한다.
4. 입력 시작 시각과 마지막 수정 시각을 구별한다.
5. 스냅샷 텍스트와 그 시각을 함께 받는다. 날짜 해석에는 전달된 시간대와 입력 시각을 확인한다.
6. 보내기나 Enter로 확정된 최종 발화를 별도로 받는다.
7. 호스트 답변과 다음 사용자 입력 사이의 경계를 확인한다.
8. 재개 시 이전 세션의 마지막으로 확인된 상태를 확인한다.
9. 미저장 처리 항목이 있는지 확인하되 임의로 확정하지 않는다.
10. 접근 권한이나 필수 컨텍스트가 없으면 처리를 보류한다.

## 시작부터 입력 중까지

로컬 M1/M2에서는 AI API의 사용 가능 상태와 선택한 저장소의 접근 가능 상태를 확인한다.
M4+의 실제 회원 인증·호스트 연결이 없다는 이유로 로컬 시뮬레이션 자체를 막지는 않는다.
테스트용 사용자·호스트 맥락과 실제 연동 정보를 구분하며, API나 저장소가 준비되지 않았으면 대화 처리 준비 완료로 표시하지 않는다.

1. 시작 조건이 충족되면 세션 컨텍스트를 준비하고 활성으로 둔다.
2. 첫 입력이 감지되면 시각을 기록하고 입력 중으로 전환한다.
3. 호스트는 입력 중 텍스트를 논블로킹으로 전달한다.
4. 기획상 전달 간격은 0.5초 쓰로틀이다. 한국어 입력 조합 중간 글자가 잠깐 보일 수 있다.
5. 같은 내용이 반복되어도 매번 새 사실로 기록하지 않는다.
6. 입력 중 문장은 미완성이므로 실제 발화로 확정하지 않는다.
7. 스냅샷의 변화는 5계율의 망설임 검토에 활용할 수 있다.
8. 현재 단서는 9계율의 가상 미래 탐색에 활용할 수 있다.
9. 타이핑이 이어지면 마지막 수정 시각을 갱신한다.
10. 보내기나 Enter가 들어오면 최종 발화와 시각을 확정한다.
11. 확정 발화를 기준으로 쩜 추출·갱신을 다시 확인한다.
12. 저장할 실제 기억과 입력 중 가정을 구분한다.

## 중단과 재개 분기

1. 타이핑 중단 시간을 마지막 입력 변화부터 센다.
2. 3초 미만이면 입력 중 흐름을 유지한다.
3. 3초 이상이면 대기 상태로 두고 재입력 가능성을 살핀다.
4. 대기 중에도 스냅샷을 최종 발화라고 간주하지 않는다.
5. 5초 이상이면 비활성 전환을 준비한다.
6. 기획서에는 현재 상태와 히스토리를 저장한 후 비활성화한다고 적혀 있다.
7. 다만 중간 스냅샷을 언제 영구 저장할지는 별도 설계가 필요하다.
8. 비활성에서 입력이 재개되면 사용자·세션 맥락을 다시 확인한다.
9. 같은 발화를 수정 중이었다면 이전 스냅샷과 새 입력을 구별한다.
10. 새로운 발화라면 이전 확정 발화와 혼동하지 않는다.
11. 비활성에서 바로 종료로 간주하지 않는다.
12. 세션 종료 요청이 있으면 최종 저장 절차로 이동한다.

## 최종 발화와 종료

- 최종 발화가 오면 입력 중 가정보다 최종 텍스트를 우선한다.
- 최종 발화를 바탕으로 실제 쩜 생성·갱신·회상을 판단한다.
- 호스트 답변 준비를 위해 필요한 쩜과 가이드를 전달한다.
- 호스트 답변 뒤에는 다음 사용자 발화가 시작될 수 있다.
- 세션 종료 때 미저장 데이터와 세션 상태를 최종 점검한다.
- 관계 정보 갱신은 기획서의 후속 마일스톤 구분을 따른다.
- 내부 상태 저장도 민감정보 최소화와 접근 경계를 지킨다.
- 종료 사실만으로 쩜이나 쩜선을 삭제하지 않는다.

## 출력과 다음 문서

출력은 상태 전환과 보류 사유를 설명하는 판단 기록이다.
신규 세션 API 또는 영구 저장 스키마를 제정하지 않는다.

- 어떤 입력 사건으로 상태가 바뀌었는지 기록한다.
- 스냅샷인지 최종 발화인지 분명하게 표시한다.
- 최종 저장이 필요한 항목과 이미 확인된 항목을 구별한다.
- 재개에 필요한 사용자·세션 맥락의 확인 여부를 남긴다.
- 추출은 [1계율](./1계율_쩜_추출_알고리즘.md)을 참조한다.
- 망설임 해석은 [5계율](./5계율_감정_감지_알고리즘_임시.md)에 맡긴다.
- 가능한 미래 대화는 [9계율](./9계율_미래_대화_탐색_알고리즘.md)에 맡긴다.

## 실패와 보류

- 타임스탬프가 없거나 역전되면 경과 시간을 임의로 계산하지 않는다.
- '오늘'·'내일'은 전달된 시간대·입력 시각으로 해석하고, 없으면 날짜를 확정하지 않는다.
- 스냅샷이 누락되면 확정 발화를 기다린다.
- 최종 발화가 오지 않았다면 중단 시간을 사실 확정 근거로 쓰지 않는다.
- 저장소 접근이 실패하면 저장 완료라고 표시하지 않는다.
- 재개 시 사용자나 세션 일치가 불확실하면 기억 처리를 보류한다.
- 비활성 전환 중 새 입력이 오면 입력 사건을 다시 확인한다.
- 종료 절차가 실패하면 완료 상태라고 단정하지 않는다.

## 가상 예시

### 1. 잠깐 멈춘 입력

- 사용자가 '그 친구가...'를 쓰고 2초 동안 멈춘다.
- 판단: 아직 입력 중이며 문장의 의미를 확정하지 않는다.
- 출력: 마지막 스냅샷을 미완성 입력으로 유지한다.

### 2. 대기 뒤 재입력

- 사용자가 3초 이상 멈췄다가 같은 문장을 고친다.
- 판단: 대기로 갔다가 입력 중으로 돌아온다.
- 출력: 이전 스냅샷을 실제 발화로 저장하지 않는다.

### 3. 비활성 뒤 재개

- 5초 이상 입력이 없어 비활성으로 전환한다.
- 잠시 뒤 사용자가 다시 타이핑한다.
- 판단: 사용자·세션을 확인하고 기존 맥락에서 재개한다.
- 출력: 비활성을 영구 종료로 기록하지 않는다.

### 4. 입력 중 마음 변경

- 스냅샷: '오늘 회사를 그만둘까...'
- 최종 발화: '오늘 회사 일이 많아서 피곤해.'
- 판단: 퇴사 계획을 확정된 쩜으로 만들지 않는다.
- 출력: 최종 발화만 실제 기억 판단으로 넘긴다.

### 5. 한국어 조합과 날짜

- 0.5초 스냅샷에 한글 조합 중간 글자가 잠깐 나타난다.
- 판단: 중간 글자의 변화만으로 망설임이나 의도 변경을 단정하지 않는다.
- 발화가 '내일 보자'라면 전달된 시간대·입력 시각에서 날짜를 해석한다.
- 시간대가 없으면 한국 사용자라고 한국 시간으로 자동 고정하지 않는다.

## 검수 기준

- 0.5초 스냅샷과 최종 발화가 분리된다.
- 한국어 입력 조합 중간 상태를 최종 표현으로 취급하지 않는다.
- 3초 대기, 5초 비활성 기준이 구별된다.
- 비활성에서 재개할 수 있으며 종료로 자동 처리되지 않는다.
- 중간 영구 저장 시점을 임의로 확정하지 않는다.
- 저장 실패를 성공으로 보고하지 않는다.
- 세션 상태와 쩜 상태를 혼동하지 않는다.
- meta를 해석하거나 Haema가 사용자에게 직접 답하지 않는다.

## 기획 근거와 미확정

- [최신 기획서](../해마.ai_최신기획서.md)의 세션 흐름과 4장 11계율을 따른다.
- [v4 스키마](../SCHEMA.md)의 쩜 상태와 구별해 세션 상태를 설명한다.
- 0.5초 쓰로틀, 3초 대기, 5초 비활성은 기획서에 명시되어 있다.
- 중간 스냅샷과 히스토리의 영구 저장 시점·형식은 미확정이다.
- 종료 신호의 세부 기준과 재개 시 보존 범위도 별도 설계가 필요하다.
