# 13계율 — 개인정보 및 민감정보 처리 알고리즘

> 기획 명세이며 구현 완료를 뜻하지 않음.
> 필요한 개인 맥락은 남기되 불필요한 고위험 식별 정보의 저장과 회상을 줄인다.

## 역할과 읽는 상황

- 새 발화에서 쩜(JJum)을 만들거나 갱신하기 전에 읽는다.
- 쩜 이름으로 .jj 파일을 만들거나 파일명을 바꾸기 전에 읽는다.
- 호스트 AI에 기억을 회상해 전달하기 전에 읽는다.
- 로컬 쩜통과 향후 서버 확장의 경계를 설명할 때 읽는다.
- 검색어: 개인정보, 민감정보, PII, 파일명 마스킹, 회상 범위, E2EE.
- 이 문서는 해마.ai의 프로젝트 요구를 정리한 기획 명세다.
- 특정 서비스의 도메인 판단은 호스트의 명시적 맥락에 맡긴다.
- Haema는 meta의 내용을 해석해 개인정보 여부를 판정하지 않는다.

## 먼저 구별할 세 가지 보호

1. **파일명 보호:** 파일 목록에 고유명과 불편한 표현이 그대로 보이지 않게 한다.
2. **저장 전 최소화:** 기억에 불필요한 고위험 식별 정보의 정밀도를 낮춘다.
3. **회상 최소화:** 저장된 내용이라도 지금 필요한 부분만 호스트에 건넨다.
4. 파일명 보호가 쩜 내부 기억의 삭제를 뜻하지 않는다.
5. 저장 전 최소화가 이미 저장된 모든 쩜의 자동 삭제를 뜻하지 않는다.
6. 회상 최소화가 쩜의 보존 상태 변경을 뜻하지 않는다.
7. 셋은 처리 시점과 대상이 다르므로 판단 기록에서도 분리한다.

## 입력과 점검 범위

1. 사용자 발화가 스냅샷인지 최종 발화인지 확인한다.
2. 개인에게 의미가 있는 쩜 후보를 먼저 식별한다.
3. 그 후보에 포함된 고유명, 연락처, 상세 위치 등을 살핀다.
4. 기억의 의미를 유지하는 데 필요한 정보인지 따진다.
5. 고위험 식별 정보가 불필요하면 저장 전에 절삭·부분 마스킹한다.
6. 쩜 이름과 실제 파일명에 서로 다른 보호 규칙을 적용한다.
7. 회상 요청 시 현재 질문에 필요한 부분만 고른다.
8. 사용자와 세션의 경계가 맞는지 확인한다.
9. 호스트가 준 서비스 맥락은 명시된 범위에서만 사용한다.
10. 이미 저장된 쩜을 손볼 때는 다른 내용을 불필요하게 훼손하지 않는다.
11. 개인 쩜 데이터가 개발 저장소에 무단 포함되지 않도록 한다.
12. 판단이 애매하면 원문 전체를 넓게 전달하지 않고 보류한다.

## 저장 전 고위험 PII 판단

- 전화번호 전체가 기억 목적에 필요하지 않다면 일부를 가린다.
- 국내 전화번호처럼 보이는 자릿수와 구분 기호도 확인하되 실값을 예시에 복제하지 않는다.
- 상세 주소는 필요한 경우 구·동 수준의 지역 맥락만 검토한다.
- 한국 주소의 도로명·번지·동·호수는 필요한 지역 맥락과 상세 위치를 나눠 본다.
- 고위험 식별번호처럼 보이는 값은 원문을 반복 기록하지 않고 저장 제외를 검토한다.
- API 키·비밀번호 같은 접근용 비밀값은 개인 기억의 재료로 저장하거나 회상하지 않는다. 서비스 설정과 쩜 저장을 구분한다.
- 개인 식별 정보가 관계의 핵심인지와 정밀한 값이 필요한지는 다르다.
- '어느 동네 카페'라는 맥락은 남기면서 동·호수는 줄일 수 있다.
- 스냅샷 속 숫자나 이름은 최종 발화에서 바뀔 수 있음을 고려한다.
- 사용자 고유 표현을 무단으로 다른 의미로 바꾸지 않는다.
- 부정 기억도 불편하다는 이유만으로 자동 삭제하지 않는다.
- 고위험 여부가 확실하지 않다면 구체값을 늘려 쓰지 않는다.
- 저장 제외의 범위와 판단 근거를 설명용 기록에 남긴다.

## 쩜 이름과 파일명 보호

- v4 스키마에서 쩜 내부 jjumName은 기억의 대표 이름이다.
- 파일명에는 보호된 maskedJJumName을 사용한다.
- 한글 고유명칭은 영문 대문자 O로 가린다.
- 예: 홍길동이라는 내부 이름의 파일명은 홍O동.jj처럼 표시한다.
- 영문 고유명칭은 한글 ㅇ으로 가린다.
- 영문 이름에서 남길 글자의 위치·개수는 아직 미확정이며, 이 문서가 구체적인 결과 파일명을 정하지 않는다.
- 욕설·비속어가 파일명에 나오면 더 강한 가림을 적용할 수 있다.
- 파일명에 가림을 적용해도 facts·events·summary를 일괄 지우지 않는다.
- 이미 가린 이름이 서로 같아질 때의 파일 충돌 처리는 별도 설계가 필요하다.
- 파일명 가림은 디스크 내용 자체의 암호화를 뜻하지 않는다.

## 회상과 전달 범위

1. 현재 대화에 필요한 쩜만 회상 후보로 둔다.
2. 호스트가 답변하는 데 필요한 사실과 맥락만 전달한다.
3. 같은 쩜에 있는 무관한 연락처나 상세 위치는 함께 보내지 않는다.
4. 사용자가 먼저 꺼낸 민감한 맥락인지 확인한다.
5. 과거 부정 사건은 지금의 위로나 이해에 필요한지 따진다.
6. 여러 쩜을 한꺼번에 보내면 불필요한 노출이 늘어나는지 점검한다.
7. 사용자 경계가 불명확하면 회상을 보류한다.
8. 호스트가 최종 발화를 맡고 Haema는 기억과 가이드만 전달한다.

`meta`는 해마가 내용을 열어 개인정보를 분류하는 영역이 아니다. 호스트는 확장 데이터를 맡기기 전에 필요한 최소화·접근 범위를 처리해야 한다.
해마가 `meta`를 해석하지 않았다는 이유로 그 내용을 안전하다고 판정하거나 회상 결과에 통째로 복제하지 않는다.

### 사용자가 기억의 사용 범위를 제한할 때

- “이 내용은 기억하지 마”는 저장 제한으로, “지금은 그 얘기 꺼내지 마”는 현재 대화의 사용 제한으로 구별한다.
- 제한이 가리키는 내용을 확인하고, 해당 범위 밖의 기억까지 임의로 지우지 않는다. 불분명하면 호스트에 확인할 재료를 준다.
- “그 기억을 삭제해”는 대상·소유자·요청 범위를 확인한 뒤 명시적 삭제 처리로 넘긴다. `pinned`의 자동 정리 면제가 사용자 삭제 요구를 막는 근거는 아니다.
- 제한을 지속적으로 기록할 위치, 색인·쩜선·이력 등 삭제 반영 범위는 별도 설계가 필요하다. 관련 절차가 없거나 실패했다면 삭제·차단이 완료됐다고 알리지 않는다.

## 보존·삭제·보안 단계

- 기본 방향은 쩜을 보존하고 쩜선의 활성도·가중치를 조절하는 것이다.
- resting은 당장 회상하지 않는 상태이며 데이터의 영구 보존을 전제한다.
- pinned는 자동 정리 면제 신호다.
- 파일명 가림을 이유로 쩜 내부 기억을 지우지 않는다.
- 자동 감쇠를 이유로 쩜을 삭제하지 않는다.
- 사용자의 명시적인 삭제 요구는 별도의 절차로 다뤄야 한다.
- 로컬 저장을 우선한다는 기획이 데이터 접근 안전의 완성 보장은 아니다.
- E2EE와 Zero-Knowledge는 기획서에서 M4+ 목표로 구분한다.
- 현재 구현이 두 보안 성질을 실제로 보장한다고 주장하지 않는다.
- 서버 확장, 키 관리, 접근 권한의 구체 방법은 별도 설계가 필요하다.

## 출력과 다음 문서

출력은 설명용 판단 기록이다. 신규 API나 저장 스키마가 아니다.

- 어떤 정보가 기억의 핵심이고 무엇이 불필요한 식별 정보인지 적는다.
- 파일명 가림과 내부 내용 최소화를 따로 적는다.
- 회상에서 전달할 정보와 제외할 정보를 구별한다.
- 판단이 애매하면 보류 사유를 적는다.
- 쩜 추출 판단은 [1계율](./1계율_쩜_추출_알고리즘.md)과 잇는다.
- 실제 내용 갱신은 [3계율](./3계율_기존_쩜_업데이트_알고리즘.md)에 넘긴다.
- 호스트 전달 여부는 [6계율](./6계율_회상_알고리즘.md)과 함께 판단한다.

## 실패와 보류

- 파일명 가림에 실패하면 원본 이름을 그대로 파일명에 쓰지 않는다.
- 마스킹된 파일명이 겹치면 덮어쓰지 않고 충돌 처리를 보류한다.
- 고위험 정보인지 모호하면 더 정밀한 형태로 저장하지 않는다.
- 쩜통 접근이 실패하면 보호 완료나 저장 완료라고 표시하지 않는다.
- 호스트의 사용자 범위가 불명확하면 기억 전달을 멈춘다.
- 암호화 상태를 확인하지 못하면 E2EE 적용이라고 표시하지 않는다.

## 가상 예시

### 1. 사람 이름과 파일명

- 발화: '홍길동은 고등학교 친구야.'
- 판단: 내부 기억에는 관계를 알아볼 이름이 필요할 수 있다.
- 파일명: 홍O동.jj처럼 한글 고유명을 가린다.
- 출력: 파일명 보호와 내부 기억 보존을 분리한다.

### 2. 영문 고유명

- 발화: 'Alice와 카페에서 만났어.'
- 판단: 파일명에는 한글 ㅇ을 쓰는 마스킹을 검토한다.
- 출력: 내부 이름과 가린 파일명을 구별한다.

### 3. 상세 주소

- 발화: '친구 집은 서울 어느 동의 구체적인 동·호수야.'
- 판단: 친구와 만난 지역은 의미 있을 수 있으나 상세 호수는 불필요하다.
- 출력: 저장 전 정밀도 축소 후보로 기록한다.

### 4. 회상 범위

- 질문: '그 카페에서 누구를 만났지?'
- 저장 쩜: 만난 친구와 함께 연락처가 들어 있다.
- 판단: 만난 사람의 관계만 답변에 필요하다.
- 출력: 연락처는 호스트에 전달할 이유가 없다.

### 5. 국내 형식의 식별 정보

- 발화에 '[전화번호]'와 '[식별번호]'가 함께 나타났다고 가정한다.
- 판단: 실제 숫자를 문서나 중간 판단 기록에 다시 적지 않는다.
- 출력: 연락 방법이 필요하다는 맥락만 남길지 검토하고 고위험 값은 보류한다.

## 검수 기준

- 한글 고유명칭에는 영문 대문자 O, 영문 고유명칭에는 한글 ㅇ을 사용하는 파일명 마스킹이 구별된다.
- 내부 기억을 파일명 보호 때문에 삭제하지 않는다.
- 고위험 PII는 저장 전에 필요한 정밀도만 남기도록 검토된다.
- 국내 전화·주소·고위험 식별번호 예시는 실값 없이 검수할 수 있다.
- 저장된 정보라도 회상에는 필요한 부분만 전달한다.
- 자동 감쇠나 resting을 삭제 근거로 삼지 않는다.
- E2EE와 Zero-Knowledge의 구현 보장을 주장하지 않는다.
- meta를 해석하지 않고 호스트만 사용자와 대화한다.

## 기획 근거와 미확정

- [최신 기획서](../해마.ai_최신기획서.md)의 개인정보·로컬 저장·M4+ 보안 구분을 따른다.
- [v4 스키마](../SCHEMA.md)의 파일명 규칙과 쩜 보존 원칙을 따른다.
- [사용 시나리오](../USAGE_SCENARIOS.md)의 친구·카페 사례를 가상 판단에 참고한다.
- 고위험 PII의 세부 목록과 저장 제외 경계는 추가 설계가 필요하다.
- 파일명 충돌, 삭제 요청 절차, 서버 보안 구현 범위도 미확정이다.
