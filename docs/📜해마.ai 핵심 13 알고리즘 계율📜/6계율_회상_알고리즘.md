# 6계율 — 회상 알고리즘

> **기획 명세이며 구현 완료를 뜻하지 않는다.** 현재 발화에 필요한 쩜을 선별해 호스트에 건넬 재료를 정한다.
> 아래 판단 기록은 설명용이며 구현된 API 타입, 확정된 점수 공식 또는 새 저장 필드가 아니다.

## 역할과 읽는 상황

최종 유저 발화와 대화 맥락에서 cue를 찾고, 쩜(JJum)과 쩜선(Seon)을 따라 관련 기억을 탐색한다.
많이 연결된 기억을 모두 내보내지 않고 지금 답변에 쓸 만한 후보만 남긴다.
호스트가 할 말과 실제 발화 여부는 해마가 결정하지 않는다.

- 읽는 때: 최종 발화가 확정되어 [1계율](./1계율_쩜_추출_알고리즘.md)의 후보 처리 뒤 회상이 필요할 때.
- 검색어: `이름`, `별칭`, `JJ-tag`, `jjtags`, `개념 cue`, `MCTS`, `weight`, `상위 N`, `토큰 상한`.
- 입력 중 스냅샷의 후보 변화는 예고 화면일 수 있으나 최종 호스트 전달용 회상과 구별한다.
- 호스트가 현재 시각을 기준으로 이야깃거리·안부 재료를 요청한 경우에도 이 문서를 읽는다. 이때는 최종 발화 대신 그 요청의 근거와 허용 범위를 사용한다.
- M1/M2 웹 콘솔은 전달 상황을 시뮬레이션한다. 실제 호스트 연동·전달 방식은 M4+ 범위다.

## 필요한 입력

1. 최종 유저 발화, 필요한 앞뒤 대화, 호스트가 명시한 cue 또는 일반적인 `hint`.
2. 같은 `ownerId`의 v4 쩜: `jjumId`, `jjumName`, `aliases`, `jjtags`, `summary`·`facts`·`events`, 관리 상태.
3. 쩜선의 `targetId`, `weight`, 선택적 `label`, `lastActivated`.
4. 회상에 쓸 수 있는 길이와 전달 규모의 상한. 수치는 호스트·제품 설정에 맡긴다.
5. 중요도·최근성·반복 언급 등을 판단할 때 이미 존재하는 기록. 빈 값을 추정해 만들지 않는다.

`meta`는 특정 서비스가 보관한 확장 정보이므로 Haema의 회상 분기 조건으로 해석하지 않는다.
다른 소유자의 쩜은 후보가 아니며, 개인정보 범위는 [13계율](./13계율_개인정보_및_민감정보_처리_알고리즘.md)을 따른다.

## 판단 순서와 분기

### 1. 현재 맥락에서 시작 단서 찾기

유저가 직접 말한 이름·별칭을 먼저 확인한다. 대화가 제공한 JJ-tag·개념 cue도 활용한다.
한국어 이름 뒤의 조사(`핑크랑`, `성수카페에`)를 살피되, 조사 제거만으로 같은 대상을 확정하지 않는다.
`그 카페`, `거기`, 생략된 주어는 앞선 대화의 지시 대상이 확인될 때만 회상 단서로 쓴다.
한국어 원문의 말투·호칭·중의성을 영문 번역으로 대체해 판단 근거를 잃지 않는다.
한 단어의 사전적 뜻만으로 유저와 관련 없는 기억을 끌어오지 않는다.
오탈자·개인 표현의 의미가 불확실하면 [2계율](./2계율_기존_쩜_탐색_알고리즘.md)에 확인 후보를 넘긴다.
호스트 `hint`는 범용 회상 방향을 돕지만 `meta` 해석을 허용하지 않는다.

### 2. 같은 소유자의 시작 쩜 확인

이름·별칭·`jjtags`와 현재 발화가 실제로 연결되는지 확인한다.
인기 쩜이라는 이유만으로 시작점이 되거나 모든 주변 쩜이 나오지 않는다.
`active`·`resting`·`merged`의 의미는 [v4 스키마](../SCHEMA.md)에 따른다.
당장 회상하지 않는 `resting`과 다른 쩜에 흡수된 `merged`를 무심코 일반 후보처럼 내보내지 않는다.
병합 관계의 해석이 필요하면 [12계율](./12계율_쩜_충돌_및_정보_갱신_알고리즘.md)을 참고한다.

### 3. 쩜선에서 연상 후보 탐색

최신 v4 기준은 **MCTS를 활용해 weight를 따라 탐색**하는 방향이다.
관련 경로를 비교하고 의미 있는 다음 쩜을 넓혀 보되, 무한히 따라가지 않는다.
같은 상대에게 라벨이 다른 쩜선은 공존할 수 있다. 회상에는 그 상대를 잇는 가장 굵은 쩜선의 근거를 사용한다.
같은 기억이 여러 경로에서 발견되어도 후보를 중복 전달하지 않는다.
탐색 순서·선택·중지 정책의 정확한 수식은 아직 정해지지 않았다.
과거 문서의 고정 홉 수를 이 계율의 새 기준으로 가져오지 않는다.

### 4. 현재 필요한 후보 선별

현재 대화와의 관련성, 쩜선 weight, 사용자에게 갖는 의미, 최근성, 반복 언급 여부를 함께 본다.
각 요소의 고정 배점이나 보너스 값은 여기서 정하지 않는다. [10계율](./10계율_중요도와_우선순위_알고리즘.md)이 우선순위를 다룬다.
선택적 Laya 판단층이 있더라도 이는 후보 관련성의 보조 검토이며 최종 결정권자가 아니다.
보조 판단이 실패하거나 근거가 부족하면 검증된 일반 판단으로 돌아간다.

### 5. 부정 기억의 노출 목적 확인

부정적인 쩜도 저장·검색 대상에서 지워서는 안 된다.
유저가 그 사건을 먼저 말했거나 현재 맥락이 분명히 요구할 때는 **알아봐 주는 재료**로 후보에 남긴다.
유저가 꺼내지 않은 상처를 새 화제로 먼저 제안하는 일은 피한다.
현재 발화와 연결되지 않은 부정 기억은 [7계율](./7계율_답변_가이드_생성_알고리즘.md)의 편안한 답변 재료인 것처럼 꾸미지 않는다.
필요하면 “부정 맥락, 선제 언급 금지”라는 판단 이유를 함께 넘긴다. 이 문장은 출력 설명이지 새 필드가 아니다.

이야깃거리는 기본적으로 긍정·중립 기억에서 고른다. 단, [PLAN의 미해결 고민 정책](../PLAN.md)에 따라
`type="고민"`이고 `jjtags`에 `미해결`이 있는 쩜은 `careful: true`인 **조심 안부** 재료로 검토할 수 있다.
이는 고민의 상세 내용을 먼저 공개하라는 뜻이 아니다. 7계율에 일반적인 안부 방향만 넘기며, 실제 발화 여부는 호스트가 정한다.
`해결`로 바뀐 고민에는 이 예외를 적용하지 않는다. 일반적인 부정 사건·인물로 예외를 확대하지 않는다.

### 6. 전달 규모 제한

쩜선의 **weight 상위 N개**를 고려하고, 전체 **토큰 상한** 안에서 필요한 내용만 추린다.
N과 토큰 수의 구체값은 이 문서에서 만들지 않는다.
강력 추천 1~3개·관련 쩜 0~13개는 근거 있는 후보가 있을 때 웹 콘솔에 보여줄 범위다.
추천할 쩜이 없으면 0개가 정상이다. 화면 칸을 채우기 위해 약한 기억을 억지로 올리지 않는다.
잘린 후보가 있었다면 그 사실과 이유를 판단 기록에 남길 수 있으나 새 API 필드를 강제하지 않는다.

## 출력과 다음 문서

출력은 후보가 된 쩜, 시작 cue, 거친 쩜선의 근거, 지금 필요한 이유, 부정 맥락 주의, 전달 범위 판단이다.
예를 들어 아래와 같이 해마의 판단을 설명할 수 있다.

> 입력: “오늘 비 오니까 그 카페 생각난다.”
> 시작 단서: “그 카페”, 비 오는 날.
> 후보: 유저가 말한 카페 쩜과 그때의 사건 쩜.
> 주의: 사건의 부정 맥락은 유저가 먼저 회상했으므로 알아봐 주는 용도로만.
> 다음: [7계율](./7계율_답변_가이드_생성_알고리즘.md)이 답변 방향을 정하고, 말은 호스트가 만든다.

회상 결과가 비어 있어도 정상이다. “모른다”는 사실을 호스트에 알릴 수 있어야 환각을 막는다.
회상과 별도의 미래 화제 후보는 [9계율](./9계율_미래_대화_탐색_알고리즘.md)이 담당한다.

후보 탐색·미리보기와 실제 회상 사용을 구별한다. `recallCount`·`lastRecalled`는 단순히 후보를 훑었다는 이유로 갱신하지 않는다.
v4의 실제 사용 의미를 따르되, 호스트의 어떤 신호로 사용을 확인하고 중복 집계를 막을지는 미확정이다.

## 가상 예시

### 예시 1 — 이름에서 연상

“이번 주말 핑크랑 뭐 하지?”에서 조사 붙은 이름과 현재 대화의 주말·약속 맥락을 찾는다.
확인된 쩜선이 친구 핑크로 이어지고 관련성이 충분하면 핑크를 후보로 올린다.
해마는 “핑크랑 뭐 안 해?”라고 직접 말하지 않고 호스트에 재료만 준다.

### 예시 2 — 이름 없는 JJ-tag 단서

“요즘 힘드네”에 대해 호스트가 `즐거움`·`스트레스 해소` cue를 제공한다.
핑크와의 좋은 기억 쩜에 해당 `jjtags`가 확인되면 후보가 될 수 있다.
없다면 유사한 즐거운 일을 지어내지 않는다.

### 예시 3 — 유저가 먼저 꺼낸 부정 기억

“안**이 약속을 어겼어”라고 유저가 말한다.
같은 인물·사건의 부정 쩜을 알아봐 주는 후보로 두되 상대 옹호나 훈계 방향으로 단정하지 않는다.
자세한 답변 재료의 선택은 7계율에 넘긴다.

### 예시 4 — 연결은 많지만 무관함

인기 장소 쩜에 쩜선이 많아도 지금 발화와 관련된 경로가 없다.
“거기 또 갈까?”의 `거기`가 어느 장소인지 확인되지 않았다면 인기 장소에 임의로 붙이지 않는다.
연결 개수만으로 13개를 채우지 않는다. 근거 있는 후보만 전달한다.

### 예시 5 — 후보 없음

처음 듣는 고유 표현이 등장했고 유저의 뜻도 확인되지 않았다.
후보 목록을 비워 두고 뜻을 확인할 질문 **후보**를 7계율에 넘긴다.

## 보류·실패 처리

- 소유자 정보가 불명확하면 다른 사람의 기억을 추측해 섞지 않는다.
- 저장소나 모델 처리에 실패하면 오류를 알리고, 이를 “관련 기억 없음”이라는 정상 결과로 바꾸지 않는다.
- cue가 모호하면 맥락 확인 전까지 강한 추천을 보류한다.
- 쩜선 대상이 없거나 깨졌다면 그 경로를 건너뛰고 유효한 후보만 사용한다.
- 토큰 상한에 닿으면 관련성이 낮은 내용을 먼저 제외하며 부족한 근거를 숨기지 않는다.
- Laya 등 선택적 보조 판단이 실패해도 안전한 기본 판단은 계속한다.
- 부정 기억의 선제 노출 여부가 애매하면 직접 언급을 보류한다.

## 검수 기준

- 이름·별칭·JJ-tag·개념 cue가 모두 가능하되 근거 없는 연상은 배제되는가?
- v4의 MCTS·weight·상위 N·토큰 상한을 따르고 고정 홉 규칙을 새 기준으로 쓰지 않는가?
- 소유자 격리, `resting`·`merged` 관리 상태, 쩜선 중복 규칙을 존중하는가?
- 부정 기억을 삭제하지 않으면서 선제 노출을 막는가?
- 후보 0개를 허용하고 화면의 추천 수를 억지로 채우지 않는가?
- 호스트의 최종 발화를 해마가 만들어 내지 않는가?
