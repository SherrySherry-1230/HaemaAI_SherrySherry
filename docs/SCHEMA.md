# 쩜(JJum) 스키마 (v5 기획안)
> v5는 미구현 기획안이다. 현재 구현·파일 검증의 기준은 v4이며, 아래 v5 항목은 저장 구조 확정이나 마이그레이션 완료를 뜻하지 않는다.
> 회상 점수 경계·쩜파워·언급 적절성·이름 원칙은 기획팀이 합의한 기준이고, 계산식·계수·저장 방식은 검증 전 제안이다.
  > 해마태그 H-tag -> 쩜태그 JJ-tag로 교체
> 확정: 2026-09-22 (기획팀) · 용어 전면 교체: 2026-09-13. 원문 출처: 마이풉 기획서 §2-1-1 "해마.AI".
> '해마세포' 구용어 -> '쩜' 으로 교체 'HCell'도 'JJum'으로 일단 교체
> v4의 구현 기준은 TypeScript 타입 `src/types/jjum.ts`를 확인한다. 이 문서의 v5 제안을 현재 코드와 동일시하지 않는다.
> 원칙: `meta`는 서비스별 자유 확장 소켓이며 **Haema는 그 내용을 해석하지 않는다** (도메인 무지).

> **생각과 기억의 최소단위, 생각점·기억점, 그래서 점이다!**
> — 쩜(jjum)은 해마(Haema)의 기본 단위. 쩜이 이어지면 쩜선(Seon)이 된다.
> - 쩜은 보존하며, 쩜선 weight는 아래의 7단계 기준으로 갱신한다.

## 공통 전제 — 대화창당 사용자 한 명

**하나의 대화창에는 언제나 사용자 한 명만 있다.** 쩜 생성·조회·동일 대상 판별·점수 계산·회상 등 모든 설계에 이 전제를 적용한다. 사용자 발화의 `나·내`는 해당 대화창의 사용자 본인 쩜을 기준으로 해석하며, 관계 표현은 그 사용자의 기억과 관계 맥락에 연결한다. AI는 **한 사용자가 여러 표현으로 가리키는 쩜**을 판별한다. 사용자와 호스트의 발화 역할은 구분한다.

## 쩜 파워 — 4개 항의 합 (v5 기획)

**해마.ai는 호스트 챗봇의 해마다.** 사용자 쩜은 호스트가 대화 상대를 기억하는 쩜이다. 쩜 파워는 호스트가 기억하는 해당 쩜의 강력함이며, 아래 네 점수 항을 더해 상시 갱신한다. 사용자 자신의 심리 상태를 평가하는 점수나 자기 성찰에 대한 보상 점수로 해석하지 않는다.

**쩜 파워 = 언급 점수 항 + 노출 기간 점수 항 + 감정 총량 점수 항 + 쩜선 점수 항**

| 항 | 재료와 결정된 기준 | 계산 상태 |
| :--- | :--- | :--- |
| 언급 점수 항 | 사용자가 먼저 의미상 해당 쩜을 가리킨 횟수 N. 타입별 α·β 적용 | `M = α × log_β(N)`, N ≥ 1 |
| 노출 기간 점수 항 | 사용자가 해당 생각·대상과 접하고 영향을 받아온 기간. 사용자 자신은 출생부터로 최대 기간. 부모는 기본적으로 긴 기간을 추정하고 대화로 보정 | 기간을 점수로 환산하는 함수 미정 |
| 감정 총량 점수 항 | 대화에서 드러나는 감정 총량. 긍정·부정 모두 크기로 누적하고 상쇄하지 않음. 단발의 강렬함과 지속되는 도트뎀·도트힐 모두 포함 | 감정 총량 추정·점수 환산 함수 미정 |
| 쩜선 점수 항 | 연결된 쩜선의 개수와 각 weight의 굵기를 함께 반영 | 여러 쩜선의 합산·환산 함수 미정 |

파워는 양의 정수로 표시하고 상한을 두지 않는 계획이다. 내부 정밀값을 정수로 표시하는 방식은 미정이다. 생성 시각만으로 사용자의 노출 기간이나 감정 총량을 산정하지 않는다.

### 언급 항의 α·β와 타입 매트릭스

- α가 커지면 같은 N의 점수가 커지고, β가 커지면 작아진다. 수학적으로 `α × log_β(N) = [α / ln(β)] × ln(N)`이므로 두 값은 하나의 세로 배율에 작용한다. β가 별도의 곡선 모양이나 포화 시점을 정하는 것으로 설명하지 않는다.
- **N=β일 때 M=α**다. β는 기준으로 삼을 언급 횟수, α는 그 시점의 언급 점수로 이해할 수 있다.
- 타입별 α·β는 [완성한 계수표](https://docs.google.com/spreadsheets/d/1T3MACATKMU_mZNewSMqJ5kj2tszxbYmyEeODyF4MF9I/edit?gid=0#gid=0)로 관리한다. 현재 로그식 표는 29개 타입이며 사용자 설정은 **α=1, β=7**, 호스트 설정은 **α=3, β=2**다. 이를 종전 초안 2·7로 되돌리지 않는다.
- 기존 α·β 소수(Prime Number) 제한과 현재 표의 사용자 α=1의 정합성은 미정이다. 현재 CSV는 입력값을 그대로 보존하며, 내보내기의 계산 가능 조건은 α>0·β>1이다. 1을 소수라고 설명하지 않는다.
- 한 쩜에 둘 이상의 타입이 있으면 평균을 적용한다는 방향은 유지한다. α·β 자체를 평균낼지, 타입별 계산 점수를 평균낼지는 아직 확정하지 않았다. 후자는 소수 제한을 보존할 수 있는 제안이다.
- 전문가 역할 에이전트의 기준 제안: 반복 언급을 기억에 강하게 반영할 가치가 크면 α를 높이고, 평소 자연스럽게 자주 등장하는 쩜이면 β를 높인다. 타입 기본값을 개인의 맥락으로 보정하고 감정 총량을 α에 중복 반영하지 않는 방향이다. 이 기준은 검증 전 설계 의견이다.
- 네 관점의 참고 의견: 심리학은 반복 선택이 갖는 의미, 관계 관점은 다음 대화의 구체적인 연결과 개인차, 마음챙김은 실제 자기 언급을 그대로 기록하면서 일시 감정을 고정 성격으로 단정하지 않는 것, 엉뚱이는 같은 대화로 기억 도움과 불필요한 되묻기를 비교하는 실험을 제안했다. 계수 변경 실험은 한 번에 한 값을 바꾸는 방향이다.
- 사용자 쩜의 파워가 높다는 이유로 호스트가 매 대화에서 “너는 어때?” 같은 질문을 반복하도록 유도하지 않는다. 상대 이해의 배경으로 활용하고 현재 화제에 필요한 쩜을 회상·가이드에서 선별한다. 파워·회상 점수·직접 언급 적절성은 각각의 목적을 따른다.

### 타입 참조와 CSV

CSV 형식은 `type_id,type_name,alpha,beta,description`이다. `type_id`는 표의 No이며 **1은 사용자, 2는 호스트**다. `type_name`은 표시 이름이므로 사용자 칸에 엔드 유저 닉네임이 들어가도 No를 유지하여 같은 설정을 찾는다.

v4의 `type:string`을 현재 구현 기준으로 유지한다. v5에서는 복수 타입의 고정 매트릭스 ID를 참조할 수 있게 설계하며 실제 필드명·저장 구조와 v4 이행은 미정이다. AI 프롬프트에는 “이 쩜의 타입을 판단하고 해당 매트릭스의 α·β를 조회하여 언급 점수에 적용한다”는 규칙을 둔다. 수식 계산과 CSV 숫자 변환은 코드가 담당하는 방향이다.

현재 Apps Script는 gid=0 로그식 표의 실제 타입 행만 UTF-8 BOM CSV로 내보낸다. 제목·작성자·그래프·타입이 없는 HEX 참고 행을 제외하고 쉼표·따옴표·줄바꿈을 보존한다. Apps Script 메뉴와 다운로드 창은 확인했으며 코어의 CSV 연결·자동 점수 계산은 아직 구현하지 않았다. 인앱 브라우저의 최종 다운로드 파일 저장은 확인하지 못했다.

## 쩜선 weight — 7단계 연결 강도 (v5 기획)

해마.ai는 호스트 챗봇의 해마다. 쩜선 weight는 호스트가 기억하는 두 쩜 사이의 연결 강도이며, 쩜 자체의 파워·턴별 회상 점수·언급 적절성과 구분한다. 이 절은 기획·스키마·파이프라인의 새 기준이며 현재 v4 코드와 기존 파일의 이행 완료를 뜻하지 않는다.

`weight`는 **0 이상이며 소수점을 포함할 수 있는 원점수**다. 관련 있는 연결은 1~7단계로 분류하고, **7.0 이상은 모두 7단계이며 원점수의 상한은 없다.** 단계는 원점수에서 판정하며 원점수를 정수로 바꾸거나 7점으로 잘라 저장하지 않는다.

| 원점수 W | 분류 | SVG 색상 | 선 굵기 |
| :--- | :--- | :--- | ---: |
| 0 ≤ W < 1 | 연관 없음 | 단계 색상 없음 | 활성 연상 연결로 취급하지 않음 |
| 1 ≤ W < 2 | 1단계 — 가장 약한 연결 | `#E4DDEE` | 1 |
| 2 ≤ W < 3 | 2단계 | `#CDC4D8` | 2 |
| 3 ≤ W < 4 | 3단계 | `#BBB4C4` | 3 |
| 4 ≤ W < 5 | 4단계 — 공동 언급으로 생성하는 기본 연결 | `#AAA1B4` | 4 |
| 5 ≤ W < 6 | 5단계 | `#90869C` | 5 |
| 6 ≤ W < 7 | 6단계 | `#71677D` | 6 |
| W ≥ 7 | 7단계 — 가장 강한 연결, 원점수 상한 없음 | `#564E61` | 7 |

- **생성:** 쩜 생성 시 함께 언급된 두 쩜을 신규 쩜선으로 연결할 때 양쪽의 기본 weight를 **4.0**으로 둔다. 이름·별칭을 해결한 실제 쩜 ID를 사용하며 같은 상대·같은 label의 기존 쩜선을 다시 생성하거나 4.0으로 덮어쓰지 않는다. 공동 언급은 연결의 출발 근거이며 구체적인 관계 label은 확인된 의미를 따른다.
- **강화:** 이후 함께 언급되는 횟수가 늘어나는 것을 강화 근거로 삼는다. 또는 호스트 AI가 두 쩜을 연관하여 실제로 언급했고, 그 연상에 대한 사용자의 피드백이 긍정적이라고 판단되면 두 쩜의 대응 쩜선을 함께 강화한다. 호스트의 단순 회상·전달·탐색만으로 강화하지 않는다.
- **중복 방지:** 같은 공동 언급이나 같은 피드백을 스냅샷·재전송·재처리로 여러 번 집계하여 강화하지 않는다. 저장은 최종 발화와 실제 호스트 답변·사용자 반응을 확인한 뒤 수행한다.
- **기존 규칙 폐기:** 고정 `+0.1`, 최대 `1`, 하루 `−0.01`, 최소 `0.1`의 기존 강화·시간 감쇠 규칙을 새 기획에서 폐기한다. 이를 7단계 점수에 재사용하지 않는다.
- **미정:** 공동 언급 누적과 긍정 피드백을 얼마나 증가시키는지의 구체적인 함수·증가량, 이력 저장 방식, 기존 v4 weight의 이행 방식. 기존 0~1 값들을 새 7단계 원점수로 자동 재해석하지 않는다.

제공된 SVG는 왼쪽부터 **7→6→5→4→3→2→1단계**다. 7단계 이상에서는 원점수가 늘어나도 시각적 단계는 7단계로 유지한다. 쩜 파워의 쩜선 점수 항에 원점수와 단계 중 무엇을 어떻게 반영할지는 별도 계산식에서 정한다.

## 회상 점수 R의 현재 분류

| R 범위 | 분류 | 처리 의미 |
| --- | --- | --- |
| `0` | 관련 없는 쩜 | 현재 대화와 관련이 없어 호스트에게 전달하지 않는다. |
| `0 < R < 1` | 후보 쩜 | 약한 관련 가능성만 있어 검토 후보로 남긴다. |
| `1 ≤ R < 3` | 관련 쩜 | 현재 대화와 관련된 쩜이다. |
| `3 ≤ R < 5` | 강력 추천 쩜 | 연상·맥락상 매우 중요하여 강하게 추천한다. |
| `R = 5` | 확정 쩜 | 사용자가 현재 발화에서 직접 언급한 쩜이다. |

이 분류는 턴별 회상 관련성만 나타낸다. `jjumPower` 같은 지속 점수나 다른 우선순위 값과 혼동하거나 대신하지 않는다.

콘솔은 등급을 원값 R로 먼저 판정한 뒤 소수 둘째 자리 이하는 버려 소수 한 자리로 표시한다. 단, `0 < R < 0.1`은 관련 없는 쩜으로 보이지 않도록 `0.1`로 표시하고, `R = 5`일 때만 `5.0`이다. 따라서 `R = 0.99`는 `0.9`, `R = 2.99`는 `2.9`, `R = 4.99`는 `4.9`로 표시한다.

## 쩜 이름 및 파일명 보호 규칙
  - 쩜들의 파일명은 사람과 AI가 알아보기 쉽도록 {{jjumName}}.jj(jj는 쩜만의 독특한 확장자 시스템)으로 하되, 다음 maskedJJumName 예외사항이 있다.
  - 쩜 내부의 jjumName은 상관없으나 사람 실명, 특정 상품이나, 브랜드가 파일명으로 노출 되면, 로컬에서 사람 혼자 보더라도 부담스러울 수 있다. 다음처럼 '파일명'일 경우만 마스킹한다.

### maskedJJumName
#### 한글 고유명칭 마스킹
    - 한글 고유명칭은 **영문 대문자 O**를 마스킹 문자로 사용한다.
    - 짧은 이름은 1글자 정도를 남기고 나머지를 O로 치환한다.
    - 긴 이름은 앞·중간·뒤의 형태를 일부 남기고 식별 가능한 핵심 부분을 O로 치환한다.
    - 여러 단어로 이루어진 명칭은 각 단어의 형태를 가능한 한 유지한다.
    - 마스킹의 목적은 내용을 없애는 것이 아니라 파일명에서만 부담을 줄이는 것
    ```
      예시 :
      홍길동 → 홍O동, 김구 → 김O, 스타벅스 돌체라떼 → 스O벅O 돌O라떼, 볼더스콘 카페 → 볼O스O 카페
      파일명은 홍O동.jj 하지만 파일 내부는 jjumName = 홍길동
    ```
#### 욕설·비속어 마스킹
  - 욕설이나 비속어가 쩜 이름으로 생성되는 경우에도 마스킹한다.
  - 욕설 자체를 파일명으로 그대로 노출하지 않는다.
      ```
      예:
      씨발롬
      → O빌O
        파일명은 O빌O.jj 하지만 파일 내부는 jjumName = 씨발롬
      ```

  - 욕설의 경우 일반적인 고유명칭보다 강하게 마스킹할 수 있다.
  - 단, 쩜의 세부 내용(facts, events, summary)까지 불필요하게 삭제하거나 변형하지 않는다.

#### 영문 고유명칭 마스

  - 영문 고유명칭은 **한글 ㅇ**을 마스킹 문자로 사용한다.


## 원칙
- 쩜 하나당 .jj 파일 하나를 사용한다.
- 파일명에는 마스킹된 jjumName을 사용한다.
- _index.jj는 이름·별칭과 jjumId를 연결하는 인덱스다.
- 인덱스가 유실되거나 불일치하면 파일 스캔으로 복구할 수 있어야 한다.
- 사용자가 손으로 수정한 .jj 파일도 반드시 v4 스키마 검증 후 로드한다.
- 깨진 파일 하나 때문에 전체 Haema가 중단되어서는 안 된다.
- 개인 쩜 데이터는 개발 저장소에 무단 커밋되지 않도록 별도로 보호한다.

### 쩜 기록 시 표현·오탈자 처리 원칙

- 사용자의 오탈자는 의미가 명확한 경우 가능한 한 교정하여 쩜에 기록한다.
- 오탈자를 교정하더라도 사용자가 실제로 사용한 원문을 임의로 다른 의미로 바꾸지 않는다.
- 사용자의 고유한 말투·표현 습관은 쩜의 내용에서 임의로 표준화하지 않으며, 필요한 경우 별도 **관계 데이터**의 말투 정보에 반영한다.
- 신조어·개인적 표현·의미가 불명확한 단어는 일반적인 사전적 의미로 임의 해석하지 않는다. (한국은 신조어가 자주, 많이 나오는 문화적 특징이 있다...)
- 해당 표현이 쩜 생성이나 회상에 중요하고 의미를 확정하기 어려운 경우, 호스트 AI를 통해 사용자에게 의미를 확인할 수 있다.
- 예: 사용자가 `"샤갈!"`이라고 표현하였을 때 이를 화가 **샤갈**로 자동 해석하지 말고, 사용자의 개인적 표현인지 확인할 수 있다.

## 사용자 언급 횟수와 동일 쩜 판별 (v5 기획)

- 쩜 파워의 언급 점수에 사용하는 `N`은 **사용자가 먼저, 의미상 해당 쩜을 가리킨 발화 횟수**다. 호스트 발화와 호스트가 먼저 꺼낸 쩜을 사용자가 따라 답하거나 반복한 경우는 포함하지 않는다. 기존 “자발 언급과 질문 답변을 똑같이 집계” 규칙은 폐기한다. v4의 `mentionCount`를 새 N으로 이행하는 구체적인 방식은 미정이다.
- **확정된 사용자 발화 하나에서 같은 쩜은 최대 1회 집계한다.** 같은 이름을 반복하거나 여러 별칭으로 가리켜도, 동일한 `jjumId`로 확인되면 한 번만 반영한다. 서로 다른 쩜은 각각 1회, 이후의 다른 사용자 발화는 별도로 집계한다.
- 한국어에서 `나`가 생략되어도 문맥상 사용자가 자신을 가리킨 언급이면 집계한다. 예: “오늘도 이렇게 복잡한 생각하기 겁내고 있다”는 사용자 본인의 생각·감정 상태를 먼저 말한 것이므로 사용자 쩜의 N을 1 올린다. 사용자 쩜의 과도한 파워를 막기 위해 실제 의미상 언급을 누락하지 않는다.
- 질문 답변을 전부 제외하는 규칙이 아니다. 호스트가 “오늘 뭐 했어?”라고 묻고 사용자가 “기타 쳤어”라고 하면 기타는 사용자가 먼저 꺼냈으므로 집계한다. “오늘 기타 쳤어?”에 “응, 기타 쳤어”라고 따라 답한 경우는 기타의 N에 더하지 않는다. 선행 언급을 비교할 대화 구간과 판정 방식의 구현 세부는 미정이다.
- AI API는 단어의 등장 횟수를 세기 위해서가 아니라, **한 사용자의 서로 다른 표현이 같은 생각의 단위를 가리키는지 문맥으로 판단하기 위해** 사용한다. 이름·별칭·번역 표기·오탈자·관계 표현을 해당 사용자의 기억과 현재 대화 맥락에 비추어 기존 쩜에 연결하고, 확인된 `jjumId`들의 중복을 제거한 뒤 코드가 횟수를 반영한다.
- 예를 들어 대화창의 사용자가 론 위즐리라면 `내 아내`, `내 안사람`, `내 여자`, `헬마이니`, `헤르미온느`는 그 사용자의 같은 배우자 쩜에 연결한다. 같은 발화에 모두 나와도 1회다. `내 아내`의 기준은 이미 정해진 그 사용자다. 인용문 속 표현은 인용 맥락을 확인하며, 대상이 불명확하면 추측으로 다른 쩜들을 합치지 않는다.
- 입력 중 스냅샷은 잠정 분석에만 사용하고 최종 발화 확정·저장 때 집계한다. 같은 발화의 재처리·재전송·저장 재시도로 중복 증가하지 않아야 한다. 발화 식별 정보와 `jjumId`를 함께 확인할 수 있어야 하며, 실제 필드명·저장 방식은 구현 전에 정한다.
- 일반 쩜은 최초 발화로 생성될 때 `mentionCount=1`이며 **그 생성 발화를 다시 더해 2로 만들지 않는다.** 두 자아쩜의 생성 시 1회 부여와 사용자가 먼저 꺼낸 첫 실제 언급 시 2회가 되는 규칙은 아래 생명주기를 따른다.
- 이 절은 v5의 집계 규칙이다. 현재 v4 코드가 문맥 판별과 발화별 중복 방지까지 구현했다는 뜻은 아니다.

## 사용자·호스트 기본 쩜의 생명주기 (v5 기획)

- **사용자 본인 쩜과 실제 대화 상대인 호스트 챗봇 쩜을 함께 생성·연결한다.** 가입 시 호스트가 확정된 서비스는 계정 생성 시, 여러 캐릭터 중 선택하는 서비스는 선택 완료 후 해당 대화창에 처음 들어갈 때 두 자아쩜을 생성·연결한다. 첫 발화나 쩜 추출을 기다리지 않으며, 선택 전 사용자 본인 쩜만 따로 생성하지 않는다.
- 같은 사용자 계정에는 하나의 사용자 본인 쩜을 연결한다. 로그인·세션 변경·생성·연결 재시도에는 기존 `jjumId`를 재사용한다. 다른 캐릭터의 대화창에 처음 들어가면 사용자 본인 쩜은 유지하고 해당 호스트 쩜만 추가한다. 이전 캐릭터로 돌아오면 그 호스트 쩜도 재사용한다.
- 계정 및 호스트와 쩜을 연결하는 고유 식별 정보와 발화자별 지칭 기준이 필요하다. 표시 이름이나 무조건적인 대명사 별칭 매칭으로 대상을 판정하지 않는다. 이 정보의 실제 필드명·저장 위치는 미정이며, 코어가 `meta`를 해석하도록 우회하지 않는다.
- 일반 쩜과 두 자아쩜(사용자 본인 쩜·호스트 쩜)은 모두 `mentionCount=1`, `recallCount=0`으로 시작한다. 일반 쩜은 사용자의 첫 언급으로, 두 자아쩜은 대화 시작 전 생성 자체를 최초 1회 언급으로 취급하여 언급 횟수 1을 부여한다. 자아쩜의 `lastMentioned`는 생성 시각으로 기록하되 실제 대화 발화를 만들어 기록하지 않는다. 초기 1회는 각 쩜의 최초 생성에만 부여하며, 이후 사용자가 해당 자아쩜을 먼저 꺼내는 첫 실제 언급을 하면 `mentionCount=2`가 된다. 재사용·로그인·새 세션·캐릭터 전환·재진입·생성·연결 재시도에서는 기존 횟수를 보존하고 추가 집계하지 않는다. 생성 시각 자체는 파워의 노출 기간이나 감정 총량을 뜻하지 않는다.
- 현재 v4의 `createJJum()`은 `mentionCount=1`, `lastMentioned=생성 시각`, `recallCount=0`으로 생성하므로 이번 생성 시 기본값 결정과 일치한다. 생성 출처·식별 정보·최초 생성·연결 경로는 구현 전에 정하며, 이 문서 변경으로 계정 연동 코드나 기존 파일이 이행된 것은 아니다.
- 초기 파워 값, 타입 목록, 계수 및 저장 필드는 별도 파워·스키마 설계에서 정한다. 상세 처리 순서는 [최신 기획서의 전체 파이프라인](해마.ai_최신기획서.md)을 따른다.

## 변경 이력

- 2026-10-08 오늘 논의한 파워 4항·로그식·αβ 의미·29개 타입 매트릭스·닉네임과 No 분리·CSV 사용을 기획에 반영. N은 사용자 선행 의미상 언급만 집계하고 생략된 자기 지칭도 포함하도록 정정. 다중 타입 평균 방식과 나머지 환산식·저장 필드는 미정.
- 2026-10-08 기존 고정 강화·시간 감쇠·1점 상한 기획을 폐기하고 쩜선 weight의 7단계 기준 확정. 공동 언급 신규 연결은 4.0, 공동 언급 누적·호스트 연상의 긍정 피드백으로 양쪽 연결 강화. 7.0 이상은 7단계이며 원점수 상한 없음. 증가량·v4 이행은 미정, 코드 변경 없음.
